## 1. 시스템 한 장 요약

```
                         ┌──────────────── 엔진 프로세스 (Python 3.13 · asyncio 단일 이벤트 루프) ────────────────┐
KIS REST  ◀── 우선순위 ──┤ PriorityRateLimiter (P0 주문 > P1 계좌 > P2 시세 > P3 백그라운드)                      │
 (HTTPS)       토큰버킷  │   └ KISClient._request: 재시도·토큰 갱신·멱등성 분기·TR별 지연 히스토그램·시계 오차       │
KIS WS    ─────────────▶ │ KISWebSocketClient: PINGPONG 에코 · 지수 백오프 재접속 · 무음 재접속 · 구독 복원 · AES │
                         │        │ 불건강(60s 무수신) → REST 폴링으로 자동 전환                                    │
                         │        ▼                                                                               │
                         │ EventBus  ┬ 무손실 채널: fill · order                                                  │
                         │           └ 손실 허용 채널: quote · signal (가득 차면 오래된 것 버림)                    │
                         │ TradingEngine: 판정 → RiskManager(최종 관문) → 주문 → 체결 대조                        │
                         │ 상태: 원장(JSONL, 대회 근거자료) · state/engine_state.json(진입일·요건 매매 표시)      │
                         └── FastAPI /api/state · /metrics(Prometheus) · /health ────────────────────────────────┘
운영: systemd(재시작·메모리 상한) · chrony · logrotate · 원장 일일 백업 · 배포 스크립트(엔진 이중 기동 차단)
```

| 항목 | 실측 |
|---|---|
| 엔진 메모리(RSS) | **약 250MB** |
| KIS REST 왕복 지연 | **50~350ms** (시세 p50 약 100ms) |
| KIS 모의투자 실효 유량 | **초당 약 1건** (문서 2건) |
| 장 시작 판정(284종목) | 분봉 개별 조회 305.0초(284호출) → **복수시세 19.8초(10호출)** |
| 시계 오차(증권사 서버 − 로컬) | **−0.7초** |

**병목은 네트워크가 아니라 증권사 유량 한도다.** 그래서 대부분의 개선은 "요청을 덜 보내고, 중요한 요청을 먼저
보내고, 실패를 정확히 분류하는 것"이었다.

## 2. 트래픽 제어 — 한정된 유량을 어떻게 나눠 쓰나

### 2-1. 우선순위 토큰 버킷 (`core/rate_limiter.py`)

- **단조시계** 기반 연속 리필(시스템 시각이 바뀌어도 안전), 대기열은 **우선순위 힙**
- 시세 조회가 몰려도 **손절·청산 주문(P0)이 맨 앞**으로 간다 — 커널 qdisc 우선순위 큐를 애플리케이션에서 구현한 것
- 서버가 초과(`EGW00201`·429)를 알리면 토큰을 비우고 **페널티 시간을 두 배씩**(최대 60초) 늘린다

### 2-2. 실측으로 한도를 다시 정했다

| 초당 요청 | 30건 중 거절 |
|---|---|
| 1.8 | 13 |
| 1.5 | 10 |
| 1.2 | 5 |
| **1.0** | **0** |

문서 한도(2건/초) + 버스트 2로 두었더니 같은 1초 창에 3건이 들어가 거절 → 5초 페널티 → 다시 거절이 반복되어
**기동 6분 동안 유량 초과 74회, 일봉 적재가 거의 진척 없음.** `RATE=1 · BURST=1`로 바꾼 뒤 **0~3회**.

### 2-3. 요청 수를 줄인다 — 배치 API

장 시작 판정은 284종목의 "장 시작 10분 거래대금"이 필요하다. 종목마다 분봉을 받으면 284호출 ÷ 1건/초 ≈ **5분** —
판정이 끝나기 전에 진입 시점이 지난다. KIS **복수시세(30종목/호출)**로 바꿔 **10호출 · 19.8초**(실측, 같은 284종목 개별 조회는 284호출 · 305.0초 — 15배).
측정에서 진입 시각 09:13 → 09:10은 성과에 차이가 없었고(P(+100%) 9.6% vs 9.1%), 지연만 사라졌다.
기준선용 분봉 기록(종목마다 필요)은 **진입 뒤 백그라운드**로 미뤘다 — 크리티컬 패스에서 빼는 것이 핵심이다.

## 3. 신뢰성 — 실패를 정확히 분류한다

### 3-1. 주문 멱등성 (`api/client.py::_request`)

주문(POST)은 **멱등하지 않다.** 같은 요청을 두 번 보내면 두 번 산다.

| 실패 | 요청이 증권사에 갔나 | 처리 |
|---|---|---|
| 접속 실패·접속 타임아웃·커넥션 풀 대기 | 안 갔다 | 재시도 |
| 429·`EGW00201` | 게이트웨이가 **거절**(실행 안 됨) | 재시도 |
| **읽기 타임아웃·연결 중 끊김·5xx** | **모른다** | **재시도 금지 → `LOCAL_UNKNOWN`** |

`LOCAL_UNKNOWN`을 받으면 엔진은 재전송하지 않고 **즉시 미체결·잔고를 조회해 대조**한다(`main._submit`).
접수됐다면 미체결 목록에서 `open_orders`로 들어와 이후 같은 종목 중복 주문을 막는다.
**예전 코드는 주문도 통신 예외마다 3회까지 재시도했다** — 응답 지연 한 번이면 45% 비중 매수가 두 번 나갈 수 있었다.
(KIS 주문 API에는 클라이언트 주문 ID(idempotency key)가 없어서, 서버 측 중복 제거에 기댈 수 없다.)

### 3-2. 무손실 채널 분리 (`core/events.py::EventBus`)

| 채널 | 토픽 | 가득 차면 |
|---|---|---|
| 무손실 | `fill` · `order` | 버리지 않는다(하루 수십 건) |
| 손실 허용 | `quote` · `signal` | 가장 오래된 것을 버린다(최신 값만 의미) |

예전에는 한 큐였고 넘치면 **토픽과 무관하게** 가장 오래된 이벤트를 버렸다 — 시세 폭주 때 체결이 버려지면 장부가
브로커와 어긋난다. 채널마다 소비자 태스크가 따로 돌아 시세 처리가 밀려도 체결 처리는 늦어지지 않는다.

### 3-3. 정합성은 브로커가 기준이다

- 손절선은 **체결 시점** 평단가로 설정(접수 시점엔 포지션이 없다)
- 부분체결은 잔량만 차감하고, 0일 때만 미체결 추적에서 지운다(먼저 지우면 중복 진입)
- 주기적으로 **브로커 잔고·미체결과 대조**해 내부 장부를 맞춘다(체결 누락 보정). 단 모의투자는 미체결·일별 체결 조회를
  지원하지 않아(`90000000`·`70070000`) 체결 폴링과 체결통보(WS) **양쪽에서** 미체결 잔량을 직접 깎는다(10/16 장애 9)
- 재시작하면 포지션은 브로커에서, 진입일·요건 매매 표시·오늘 판 종목은 상태 파일에서 복구한다. 장 시작 판정 시각을 2분 넘겨
  기동하면 그날 장 시작 판정은 건너뛴다(누적 거래대금이 창보다 길어져 다른 판정이 된다) — **다른 모드(Mock)의 상태는 복구하지 않는다**

### 3-4. 실시간 연결

PINGPONG 즉시 에코 · 지수 백오프 재접속 · **구독 자동 복원** · 60초 무수신이면 REST 폴링으로 폴백.
평일 08~16시 무음 180초면 끊고 재접속(장 밖 30분) — 10/29 연결이 `ESTAB`인 채 엿새 메시지 0건이었다. 커널 keepalive는
TCP 생존만 보므로 애플리케이션 정지는 애플리케이션이 잡아야 한다(장애 12).

### 3-5. 시계

09:10 판정은 로컬 시계로 돈다. KIS 응답의 `Date` 헤더(1초 해상도)와 비교해 **왕복 절반을 보정한 오차**를 기록하고,
2초 이상이면 경고한다. 서버는 chrony로 동기화한다.

## 4. 관측성 — 숫자로 본다 (`/metrics`, Prometheus 형식)

| 지표 | 의미 |
|---|---|
| `kis_http_request_seconds{tr=...}` (히스토그램) | TR별 왕복 지연 — p50/p95/p99 |
| `kis_http_requests_total{tr,outcome}` | TR별 결과(ok·429·500·error) |
| `kis_rate_limit_rejects` · `kis_rate_limit_wait_ms` | 유량 거절 누적 · 평균 대기 |
| `kis_event_dropped` | 손실 채널에서 버린 시세(체결은 0이어야 한다) |
| `kis_clock_skew_seconds` | 증권사 서버 − 로컬 |
| `kis_equity` · `kis_drawdown_pct` · `kis_positions` | 비즈니스 지표 |

**히스토그램을 고정 버킷으로 둔 이유:** 표본을 다 들고 있으면 장중 수만 건이 쌓인다. Prometheus처럼 경계별 누적
카운트만 들고 분위수는 버킷 경계로 근사한다(메모리 O(버킷 수)). 평균은 꼬리를 숨기므로 p95/p99를 본다.

## 5. 운영 (`deploy/oracle/`)

| 항목 | 설정 | 이유 |
|---|---|---|
| 프로세스 관리 | systemd `Restart=always` · `RestartSec=30` | 죽거나 재부팅돼도 다시 뜬다 |
| 종료 | `TimeoutStopSec=60` | SIGTERM 뒤 미체결 취소·상태 저장 시간 |
| 자원 상한 | `MemoryMax=2G` (실측 RSS 250MB) | 누수가 나면 서버 전체가 아니라 서비스만 재시작 |
| 시간 | chrony · `Asia/Seoul` | 판정 시각 정확도 |
| 로그 | logrotate 일 단위 30일 · `copytruncate` | 디스크 고갈 방지, 엔진 재시작 없이 |
| 비밀 | `.env` 600 · SSH 키 전용(비밀번호 로그인 끔) | 22번이 외부에 열려 있다 |
| 커널 | `tcp_keepalive_time=60` 등 | 죽은 연결을 2시간이 아니라 약 2분 안에 정리 |
| 백업 | 평일 15:40 원장·상태 압축, 30일 보관 | 대회 근거자료 |
| 배포 | `deploy.sh switch`는 노트북 엔진을 먼저 멈추고 확인한 뒤 서버를 켠다 · **장중(08:30~15:40) 전환 거부** | 같은 계좌에 엔진 둘 = 이중 주문 |
| 예약 배포 | 노트북을 못 켜 둘 때: 커밋을 서버 별도 폴더에 올리고 `systemd-run --on-calendar`로 장 마감 뒤 셀프테스트 → 정지 → 교체(백업) → 기동 확인, 실패 시 자동 되돌림(11/04) | 사람이 없어도 장중 재시작 없이, 실패해도 이전 상태로 |
| 버전 고정 | `requirements-lock.txt`(노트북과 같은 버전) | 모델 피클이 버전에 묶여 있다 |
| 줄바꿈 | `.gitattributes` `*.sh eol=lf` | 윈도우 저장소의 CRLF 가 리눅스 셸 스크립트를 깨뜨린다 |

**노트북 운영(서버 이전 전):** `scripts/run_live.ps1` — 독립 프로세스(개발 도구의 메모리 정리 대상이 아님) ·
엔진이 끝나면 30초 뒤 재시작 · `logs/STOP` 파일로 정지.

## 7. 하지 않은 것 (그리고 이유)

| 후보 | 하지 않은 이유 |
|---|---|
| 마이크로서비스 분리 · 메시지 브로커(Kafka 등) | 프로세스 1개 · 하루 주문 수십 건. 분리하면 장애 지점과 직렬화 비용만 늘어난다 |
| 서킷 브레이커 라이브러리 | 증권사가 하나뿐이라 열어 봐야 갈 곳이 없다. 대신 유량 페널티·재시도 분류·REST 폴백으로 같은 효과 |
| HTTP/2 | 동시 요청 자체가 유량(1건/초)으로 막혀 다중화 이득이 없다 |
| 다중 증권사(토스·나무) 병렬 조회 | 출처마다 IP 화이트리스트·장애 지점·데이터 정의가 늘어난다. 판정 데이터는 체결과 같은 출처(KIS)로 통일 |
| 커스텀 TCP 게이트웨이 | 소비자가 하나라 의미가 없다 — 전략 프로세스가 여럿이 되면 그때(설계는 별도 문서) |
