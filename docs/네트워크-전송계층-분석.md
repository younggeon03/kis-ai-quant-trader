# 네트워크·전송 계층 분석과 개선안 — BanKis16

> 작성 2026-10-13. 대상: 이 저장소(Python 3.13 · asyncio). 실거래는 KIS Open API(모의투자 서버)만 썼다.
> 대회(2026-10-12 ~ 11-20)는 끝났고 엔진은 11/22에 멈췄다. 이 분석과 제안은 대회 2일차 기준이며 제안한 게이트웨이는 만들지 않았다.

> 의미가 있는지**를 구분해 제안한다. 개선 효과를 숫자로 확인할 수 있도록 측정 방법까지 적는다.

## 0. 먼저 결론

| 구간 | 지금 | 병목 | 커스텀 TCP/바이너리의 효과 |
|---|---|---|---|
| **증권사 ↔ 엔진** (KIS REST·WS) | HTTP/1.1 keep-alive · WebSocket(텍스트 프레임) | **증권사 유량 한도(모의 실효 초당 약 1건)** | **바꿀 수 없다** — 프로토콜은 증권사가 정한다. 개선은 "요청 수 줄이기"(복수시세 30종목/호출)에서 나왔다 |
| **엔진 내부** (시세→전략→주문) | 한 프로세스 · asyncio · 인메모리 큐 | 없음(직렬화 자체가 없다) | 프로세스를 나누지 않는 한 **0** |
| **엔진 ↔ 대시보드** | HTTP 2초 폴링 · JSON | 없음(1명이 본다) | 체감 없음 |
| **(신설) 시세 게이트웨이 ↔ 전략 엔진 N개** | 없음 | — | **여기가 유일하게 의미 있는 자리** — 세션 1개를 여러 소비자에게 팬아웃할 때 |

**정직한 요약:** 이 시스템의 지연은 네트워크가 아니라 **증권사 유량 한도**가 지배한다. 실측(2026-10-13)에서 284종목
분봉 조회 305.0초 → 복수시세 19.8초(15배)는 "요청 수를 284회에서 10회로 줄인" 결과이지 전송 계층 튜닝이 아니다.
커스텀 TCP는 **증권사 세션을 하나만 쥐고 여러 전략 프로세스에 시세·주문을 중계하는 게이트웨이**를 만들 때
가치가 생긴다(KIS WebSocket 구독 41건 한도를 여러 소비자가 나눠 쓰는 구조).

## 1. 이미 적용된 전송 계층 기술 (파일·클래스별)

### 1-1. REST 연결 관리 — `api/client.py::KISClient.connect`

```python
httpx.AsyncClient(base_url=..., timeout=httpx.Timeout(HTTP_TIMEOUT),
                  limits=httpx.Limits(max_connections=20, max_keepalive_connections=10))
```

| 요소 | 평가 |
|---|---|
| **커넥션 풀 + keep-alive** | 요청마다 TCP·TLS 핸드셰이크를 하지 않는다. 같은 호스트에 1~2개 연결이면 충분한데 풀이 20이라 과하다(유량 1건/초) |
| HTTP/1.1 | HTTP/2(`http2=True`, 다중화)로 바꿀 이득이 적다 — 동시 요청 자체가 유량 한도로 막힌다 |
| 재시도 | 통신 오류는 지수 백오프(`HTTP_BACKOFF_BASE x 2^n`), 429·`EGW00201`은 유량 제어기에 페널티 통지 |

### 1-2. 유량 제어 — `core/rate_limiter.py::PriorityRateLimiter`

- **단조시계 토큰 버킷**(시스템 시각 변경에 무관) + **우선순위 힙**: 주문 P0 > 계좌 P1 > 시세 P2 > 백그라운드 P3
- **적응형 페널티**: 서버가 초과를 알리면 토큰을 비우고 대기 시간을 두 배씩 늘린다(최대 60초)
- **관측**: 승인 수·대기 평균/최대·실측 RPS·1초 창 피크(`peak_rps`)를 `/metrics`로 노출

**평가 — 이 프로젝트에서 가장 잘 된 "전송 계층" 장치다.** 흔히 커널 큐잉(qdisc)이 하는 우선순위 스케줄링을
애플리케이션 레벨로 끌어올린 것이고, 시세 폭주 중에도 손절 주문이 밀리지 않는다.
**실측으로 고친 것(2026-10-13):** 모의투자 문서 한도는 2건/초지만 실효 한도는 약 1건/초였다
(1.0건 거절 0 · 1.2건 30중 5 · 1.5건 30중 10 · 1.8건 30중 13). 버스트 2를 허용하면 같은 1초 창에 3건이 들어가
거절 → 5초 페널티 → 같은 패턴 반복으로 기동이 멈췄다. `RATE=1 · BURST=1`로 고쳤다.

### 1-3. 실시간 시세 — `core/websocket_client.py::KISWebSocketClient`

KIS 실시간은 WebSocket 위의 **텍스트 기반 커스텀 프레이밍**이다.

```
<암호화 0|1> | <TR_ID> | <건수> | <필드^필드^...^필드>      ← 한 프레임에 여러 체결이 이어 붙는다
```

| 이미 하는 것 | 위치 | 전송 계층 관점 |
|---|---|---|
| **레코드 경계 처리** — 한 프레임 안 N건을 **머리의 건수로 나눈** 스트라이드로 자르고, 구독하지 않은 코드는 버린다(11/04~. 46필드 고정은 모의서버에서 어긋나 가짜 종목·가격 23,890건) | `_parse_trade` · `_handle_realtime` | 애플리케이션 레벨 프레이밍(뭉침 처리) |
| **애플리케이션 하트비트** — `ping_interval=None`으로 라이브러리 핑을 끄고 서버 `PINGPONG`을 즉시 에코 | `_handle_control` | TCP keep-alive 와 별개인 L7 생존 확인 |
| **재접속** — 지수 백오프 + **구독 목록 자동 복원** | `_run` · `_resubscribe_all` | 세션 복구 |
| **슬롯 관리** — 세션당 41건 한도를 우선순위로 축출 | `subscribe` · `_lowest_priority_sub` | 자원 한도의 애플리케이션 관리 |
| **페이로드 암호화** — 체결통보 AES-256-CBC 복호화 | `_aes_cbc_decrypt` | 전송 보안 위의 메시지 보안 |
| **장애 감지 → 폴백** — 60초 무수신이면 `is_healthy()=False` → REST 폴링으로 전환 | `is_healthy` · `main._refresh_quotes` | 이중화 |
| **데이터가 멈춘 연결 끊기** — TCP는 살아 있는데(keepalive 통과·`ESTAB`) 메시지가 안 오면, `recv()`를 `wait_for`로 감싸 평일 08~16시 무음 180초(장 밖 30분)면 끊고 재접속(11/04~) | `_run` · `_silence_limit` | 애플리케이션 레벨 유휴 타임아웃 |

**고도화 여지:**
1. **정체(silence)와 단절을 구분**하지 않는다 — 장 마감 후 체결이 없으면 건강해도 60초 뒤 비정상 판정. 거래 시간 인지형 판정이 필요
   (재접속 쪽은 11/04에 거래 시간을 보게 했다 — `_silence_limit`. **실제로 10/29 09:50~11/04 연결이 `ESTAB`인 채 메시지 0건으로 엿새 갔다** — TCP keepalive(60초)는 상대 커널이 답하니 끊지 않는다:
   `is_healthy()`가 REST로 폴백시켜 시세는 살았지만 재접속은 없어 체결통보가 끊겼다. 폴백만 있고 복구가 없던 구조였다)
2. 파싱이 `str.split("^")` 기반이라 할당이 많다 — 초당 수천 건이면 `memoryview` 기반 스캐너가 유리(지금 부하에선 불필요)
3. 수신 시각을 파싱 시점 `datetime.now()`로 찍는다 — **수신 소켓 시각**과 섞여 지연 측정이 부정확

## 2. 커스텀 TCP/바이너리를 붙일 자리 — "시세·주문 게이트웨이"

### 2-1. 왜 여기인가

KIS는 **계정당 WebSocket 세션·구독 41건·REST 유량**이 한정 자원이다. 전략을 여러 프로세스로 나누면(예: 장 시작
판정 / 장중 감시 / 리스크 감시) 각자 KIS에 붙어 한도를 나눠 먹는다. 그래서 **게이트웨이 하나가 KIS 세션을 독점**하고
내부 소비자들에게 시세를 팬아웃하고 주문을 모아 보낸다 — 거래소·증권사 내부의 **피드 핸들러 / 주문 게이트웨이** 구조다.

```
                ┌──────────────── 게이트웨이 (Netty, JVM) ────────────────┐
KIS WS ───────▶ │ WS 수신 → 파싱 → 정규화 → Tick(바이너리)  ──팬아웃──┐    │
KIS REST ◀────▶ │ 주문 큐(우선순위·유량)  ◀── Order(바이너리) ◀──┐   │    │
                └──────────────────────────────────────────────│───│────┘
                                         TCP(길이 프리픽스) ──┘   │ UDP 멀티캐스트(선택)
                                                             전략 엔진 A, B, ... (Python asyncio)
```

| 채널 | 전송 | 이유 |
|---|---|---|
| 주문·체결 | **TCP + 순번 + ACK** | 하나도 잃으면 안 된다. 순서 보장 |
| 시세 | TCP(기본) 또는 **UDP 멀티캐스트**(선택) | 최신 값만 의미. 소비자가 많으면 멀티캐스트가 송신 비용을 1회로 만든다 — 대신 순번으로 갭 감지 |

### 2-2. 프레임 설계 (TCP Framing)

TCP는 바이트 스트림이라 **메시지 경계가 없다** — 한 번의 `read`에 반 메시지(조각남)나 1.5메시지(뭉침)가 온다.
그래서 **길이 프리픽스 헤더**를 둔다.

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 2 | magic `0xBA16` | 동기 확인(스트림이 어긋나면 즉시 끊는다) |
| 2 | 1 | version | 프로토콜 버전 |
| 3 | 1 | type | 1=Tick 2=Order 3=Ack 4=Fill 9=Heartbeat |
| 4 | 4 | length | **본문 길이**(헤더 제외) |
| 8 | 8 | seq | 채널별 단조 증가 순번(갭·중복 감지) |
| 16 | 8 | ts_ns | 송신 시각(ns, 지연 측정용) |
| 24 | N | body | 타입별 고정 레이아웃 |

**Tick 본문(고정 40바이트)** — JSON(`{"symbol":"005930","price":236000,...}`) 약 150바이트 → 40바이트

| 필드 | 형식 | 바이트 |
|---|---|---|
| symbol | ASCII 6자 + 패딩 | 8 |
| price | int64(원) | 8 |
| volume (누적) | int64 | 8 |
| turnover (누적, 원) | int64 | 8 |
| exch_ts_ms | int64 | 8 |

가격은 **정수(원)**로 보낸다 — 호가단위가 정수라 부동소수 오차가 없다(주문가 정렬 `round_to_tick`과 같은 원칙).

## 3. PoC 코드

### 3-1. Netty 서버(게이트웨이 측, Java 21)

```java
public final class GatewayServer {
    public static void main(String[] args) throws Exception {
        EventLoopGroup boss = new NioEventLoopGroup(1);
        EventLoopGroup workers = new NioEventLoopGroup();      // 코어 수만큼
        try {
            new ServerBootstrap()
                .group(boss, workers)
                .channel(NioServerSocketChannel.class)
                .option(ChannelOption.SO_BACKLOG, 1024)
                .childOption(ChannelOption.TCP_NODELAY, true)            // Nagle 끔 — 작은 메시지 즉시 송신
                .childOption(ChannelOption.SO_KEEPALIVE, true)           // 커널 keep-alive(죽은 피어 정리)
                .childOption(ChannelOption.SO_SNDBUF, 1 << 20)           // 1MB — 순간 폭주 흡수
                .childOption(ChannelOption.SO_RCVBUF, 1 << 20)
                .childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
                             new WriteBufferWaterMark(256 << 10, 1 << 20)) // 느린 소비자 역압
                .childOption(ChannelOption.ALLOCATOR, PooledByteBufAllocator.DEFAULT)
                .childHandler(new ChannelInitializer<SocketChannel>() {
                    @Override protected void initChannel(SocketChannel ch) {
                        ch.pipeline()
                          // [조각남/뭉침] length 필드(오프셋 4, 4바이트)로 정확히 한 프레임씩 잘라 준다
                          .addLast(new LengthFieldBasedFrameDecoder(64 << 10, 4, 4, 16, 0))
                          .addLast(new FrameDecoder())                    // ByteBuf → Frame 객체
                          .addLast(new FrameEncoder())                    // Frame → ByteBuf
                          .addLast(new IdleStateHandler(15, 5, 0, TimeUnit.SECONDS)) // 하트비트
                          .addLast(new HeartbeatHandler())
                          .addLast(new SessionHandler());                  // 구독 등록·주문 수신
                    }
                })
                .bind(9100).sync().channel().closeFuture().sync();
        } finally {
            boss.shutdownGracefully(); workers.shutdownGracefully();
        }
    }
}
```

`LengthFieldBasedFrameDecoder(maxFrame, lengthFieldOffset=4, lengthFieldLength=4, lengthAdjustment=16, initialBytesToStrip=0)`
— 길이 필드 뒤에 seq(8)+ts(8)=16바이트가 더 있으므로 `lengthAdjustment=16`. 반 프레임이면 버퍼에 쌓아 두고
기다리고, 여러 프레임이 붙어 오면 하나씩 잘라 다음 핸들러로 넘긴다.

```java
/** Tick → ByteBuf. 객체를 거치지 않고 풀 버퍼에 직접 쓴다(GC 압력 최소화). */
final class FrameEncoder extends MessageToByteEncoder<Frame> {
    @Override protected void encode(ChannelHandlerContext ctx, Frame f, ByteBuf out) {
        out.writeShort(0xBA16).writeByte(1).writeByte(f.type())
           .writeInt(f.bodyLength()).writeLong(f.seq()).writeLong(System.nanoTime());
        f.writeBody(out);   // Tick: symbol(8) price(8) volume(8) turnover(8) exch_ts(8)
    }
}

/** 쓰기 유휴 5초면 핑, 읽기 유휴 15초면 끊는다(L7 하트비트 — KIS PINGPONG 과 같은 역할). */
final class HeartbeatHandler extends ChannelDuplexHandler {
    @Override public void userEventTriggered(ChannelHandlerContext ctx, Object evt) {
        if (evt instanceof IdleStateEvent e) {
            if (e.state() == IdleState.WRITER_IDLE) ctx.writeAndFlush(Frame.heartbeat());
            else if (e.state() == IdleState.READER_IDLE) ctx.close();   // 상대가 죽었다
        }
    }
}
```

**느린 소비자:** 채널이 `isWritable()==false`(고수위 초과)면 시세는 **최신 값으로 덮어쓰고(conflation)** 주문·체결은
절대 버리지 않는다 — 1-4의 이벤트 버스 결함과 같은 원칙을 전송 계층에서 지킨다.

### 3-2. Python 소비자(전략 엔진 측) — asyncio streams

```python
import asyncio, struct

HEADER = struct.Struct(">HBBIqq")          # magic, ver, type, length, seq, ts_ns  (24바이트)
TICK = struct.Struct(">8sqqqq")            # symbol, price, volume, turnover, exch_ts (40바이트)

async def consume(host="127.0.0.1", port=9100, on_tick=None):
    reader, writer = await asyncio.open_connection(host, port)
    sock = writer.get_extra_info("socket")
    sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
    expected = None
    while True:
        head = await reader.readexactly(HEADER.size)      # ← 조각남 처리: 정확히 24바이트가 올 때까지
        magic, ver, typ, length, seq, ts_ns = HEADER.unpack(head)
        if magic != 0xBA16:
            raise ConnectionError("프레임 동기 깨짐")
        body = await reader.readexactly(length)           # ← 뭉침 처리: 정확히 length 만큼만 소비
        if expected is not None and seq != expected:
            log_gap(expected, seq)                         # 순번 갭 → 스냅샷 재요청
        expected = seq + 1
        if typ == 1:
            sym, price, vol, tov, ex_ts = TICK.unpack(body)
            await on_tick(sym.rstrip(b"\0").decode(), price, vol, tov, ex_ts)
```

`readexactly`가 핵심이다 — 커널이 몇 바이트씩 주든 정확히 헤더 길이·본문 길이만큼 모일 때까지 기다린다.

### 3-3. 적용 순서 (기존 구조를 해치지 않게)

| 단계 | 내용 | 기존 코드 변경 |
|---|---|---|
| 0 | **이벤트 버스 채널 분리** — 시세(덮어쓰기) / 체결·주문(무손실) | `core/events.py`만 |
| 1 | 게이트웨이를 **그림자 모드**로: KIS WS를 받아 바이너리로 재송신, 엔진은 기존 경로 유지 · 두 경로 값 대조 | 없음 |
| 2 | 엔진의 시세 입력을 게이트웨이로 전환(`AbstractBroker` 뒤에 `GatewayBroker` 추가) | 브로커 팩토리 1곳 |
| 3 | 주문도 게이트웨이 경유(순번·ACK·재전송) — **유량 제어기를 게이트웨이로 이관** | `_submit` 경로 |
| 4 | 소비자 2개 이상이 되면 시세를 UDP 멀티캐스트로(선택) | 없음 |

이 프로젝트의 원칙(브로커 메서드는 Mock·실서버에 동시에, 모든 REST는 유량 제어기 통과)과 맞게, 게이트웨이도
`AbstractBroker`를 구현하는 하나의 브로커로 끼워 넣는다.

## 4. 커널·OS 튜닝 포인트 (리눅스 서버 배포 시)

| 항목 | 설정 | 이유 |
|---|---|---|
| Nagle | 소켓 `TCP_NODELAY=1` | 작은 프레임(40~64B)을 모아 보내느라 생기는 수십 ms 지연 제거 |
| 지연 ACK | `TCP_QUICKACK`(리눅스) | Nagle과 지연 ACK가 겹치면 40ms 정체가 생긴다 |
| 버퍼 | `net.core.rmem_max / wmem_max = 4194304` · `net.ipv4.tcp_rmem = 4096 87380 4194304` | 순간 폭주 흡수. 너무 크면 지연이 버퍼에 숨는다(bufferbloat) — 측정으로 정한다 |
| keep-alive | `net.ipv4.tcp_keepalive_time=60` (기본 7200초) | 죽은 연결을 2시간이 아니라 1분 안에 정리 |
| 연결 대기 | `net.core.somaxconn=1024` | 재접속 폭주 시 SYN 유실 방지 |
| 혼잡 제어 | `net.ipv4.tcp_congestion_control=bbr` | 손실이 있는 WAN 구간(클라우드↔증권사)에서 처리량 안정 |
| CPU | 게이트웨이 수신 스레드 코어 고정(`taskset`) · `irqbalance` 조정 | 캐시 지역성 · 지터 감소 |

## 5. 측정 방법

| 지표 | 측정 | 도구 |
|---|---|---|
| **틱 전달 지연** | 게이트웨이 송신 `ts_ns` → 소비자 수신 시각 차 (같은 호스트 `CLOCK_MONOTONIC`) | HdrHistogram — p50/p99/p99.9 |
| **처리량** | 초당 프레임 수 · 바이트 수(합성 틱 부하 생성기) | JMH(직렬화), 자체 부하 생성기 |
| **직렬화 비용** | JSON vs 바이너리 인코딩/디코딩 ns/건 · 할당 바이트/건 | JMH `-prof gc` |
| **유실·순서** | 순번 갭 수 · 재전송 수 | 게이트웨이 카운터 → `/metrics` |
| **세션 복구 시간** | 강제 단절 → 재구독 완료까지 | 장애 주입(iptables DROP) |

**비교 기준을 반드시 같이 적는다:** "JSON/WebSocket 경로 p99 X ms → 바이너리/TCP 경로 p99 Y ms (같은 호스트 · 같은 부하
N틱/초 · 10분)". 이미 있는 실측값도 함께 쓸 수 있다 — **복수시세 전환으로 284종목 판정 305.0초 → 19.8초**,
**유량 실측으로 기동 정체(유량 초과 74회/6분) → 0~3회**.
