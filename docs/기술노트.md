# 기술노트 — BanKis16 으로 배우는 실무 백엔드·운영 기술

이 노트는 BanKis16 저장소를 교재로 삼아 외부 API 연동, 유량 제어, 비동기 처리, 관측, 배포·서버 운영을 공부하는 노트다.
BanKis16 은 한국투자증권(KIS) Open API 로 대회 계좌에 실제 주문을 내는 자동매매 엔진이다. 매매 전략 자체는
[매매전략.md](매매전략.md)에 있고, 이 노트는 **그 전략을 24시간 돌리는 서버 쪽 기술**만 다룬다.

독자는 파이썬 문법은 알지만 토큰 버킷, 멱등성, cgroup, SOCKS 같은 실무 용어는 처음 보는 주니어로 잡았다.
각 기술은 "기초부터 → 이 프로젝트에서는 → 실무에서는" 순서로 쓴다. 숫자는 모두 이 저장소의 코드·로그·실측에서 나왔다.

## 0. 용어집

본문에서 처음 나오는 실무 용어를 갈래별로 모았다. 셋째 칸은 이 저장소에서 그 개념이 있는 곳이다.

### 0.1 웹과 네트워크

| 용어 | 뜻 | 이 저장소에서 |
|---|---|---|
| **REST API** | HTTP 요청 한 번에 응답 한 번을 받는 방식의 서버 인터페이스다. 편지를 보내고 답장을 받는 것과 같다. | KIS 시세·주문 조회 전부(`api/client.py`) |
| **WebSocket** | 연결을 한 번 열어 두고 서버가 원할 때마다 데이터를 밀어 주는 양방향 통신이다. 전화를 끊지 않고 계속 듣는 것과 같다. | 실시간 시세·체결 통보(`core/websocket_client.py`) |
| **HTTP 상태 코드 · 429 · 403** | 응답의 성공·실패 종류를 나타내는 세 자리 숫자다. 429 는 "너무 자주 보냈다", 403 은 "권한이 없다"는 뜻이다. | KIS 429 처리(2.1절), 토스 403(IP) 처리(9.2절) |
| **IP 화이트리스트 · egress IP** | 등록된 IP 에서 온 요청만 받는 접근 제어다. egress IP 는 내 요청이 바깥으로 나갈 때 상대가 보는 출발지 주소다. | 토스 API(9.2절) |
| **프록시 · SOCKS5 · SSH 터널** | 프록시는 요청을 대신 전달해 주는 중계 서버다. SOCKS5 는 그 중계 규약이고, SSH 터널은 이미 열려 있는 SSH 연결 위에 그 중계를 만드는 방법이다. | 노트북 수집기 → 서버 → 토스(9.2절) |
| **TCP keepalive** | 오래 조용한 연결이 아직 살아 있는지 운영체제가 주기적으로 확인하는 기능이다. | `deploy/oracle/setup.sh` 커널 설정(8.4절) |
| **DNS** | 도메인 이름을 IP 주소로 바꿔 주는 전화번호부다. 회선이 끊기면 `getaddrinfo failed` 로 먼저 실패한다. | 수집 중 회선 끊김(9.2절) |

### 0.2 비동기와 동시성

| 용어 | 뜻 | 이 저장소에서 |
|---|---|---|
| **asyncio · 이벤트 루프** | 스레드 하나가 "기다리는 동안 다른 일"을 번갈아 처리하는 파이썬 비동기 실행 방식이다. 주방장 한 명이 여러 냄비를 돌려 보는 것과 같다. | 엔진 전체(`main.py::TradingEngine.run`) |
| **태스크 · 코루틴** | 코루틴은 `async def` 로 만든 멈췄다 이어갈 수 있는 함수이고, 태스크는 그것을 이벤트 루프에 올려 따로 돌게 한 것이다. | 판정·기록·스캔 태스크(5.1절) |
| **큐 · 우선순위 힙** | 큐는 먼저 온 것을 먼저 꺼내는 대기열이다. 우선순위 힙은 급한 것을 먼저 꺼내는 대기열이다. | 유량 제어 대기열(3.2절), 이벤트 버스(5.2절) |
| **락(Lock)** | 여러 코루틴이 같은 자원을 동시에 바꾸지 못하게 막는 자물쇠다. | 토큰 발급(`core/auth.py`), 원장 쓰기(`utils/logger.py`) |
| **백프레셔 · 손실 허용 채널** | 소비자가 못 따라올 때 생산을 늦추거나 오래된 것을 버리는 대응이다. | 시세는 버리고 체결은 버리지 않는 이벤트 버스(5.2절) |

### 0.3 신뢰성과 장애 대응

| 용어 | 뜻 | 이 저장소에서 |
|---|---|---|
| **유량 제한(Rate Limit)** | 서버가 일정 시간에 받는 요청 수의 상한이다. 넘으면 거절한다. | KIS 모의투자 실효 초당 1건(3장) |
| **토큰 버킷** | 일정 속도로 토큰이 차는 바구니에서 요청마다 토큰 하나를 꺼내 쓰게 하는 유량 제어 알고리즘이다. | `core/rate_limiter.py`(3.1절) |
| **버스트** | 토큰이 쌓여 있을 때 한꺼번에 나갈 수 있는 요청 수다. 바구니 크기다. | `REST_BURST=1`(3.4절) |
| **재시도 · 지수 백오프** | 실패하면 다시 보내되, 실패가 이어질수록 기다리는 시간을 두 배씩 늘리는 방식이다. | KIS 재시도·페널티(2.1·3.3절), WebSocket 재연결(4.2절) |
| **멱등성** | 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질이다. 조회는 멱등하고 매수 주문은 멱등하지 않다. | 주문 재시도 금지(2.3절), 설치 스크립트(8.2절), 수집 이어받기(9.1절) |
| **대사(Reconcile)** | 내 장부와 상대(브로커)의 장부를 주기적으로 맞춰 보는 일이다. | `_sync_portfolio`·`_sync_open_orders`(5.3절) |
| **그레이스풀 셧다운** | 종료 신호를 받으면 하던 일을 정리(미체결 취소·상태 저장)한 뒤 끄는 방식이다. | `main.py::shutdown`(5.4절) |
| **폴백** | 주 경로가 죽으면 다른 경로로 대신 처리하는 것이다. | WebSocket 이 죽으면 REST 로 시세 조회(4.3절) |

### 0.4 데이터와 저장

| 용어 | 뜻 | 이 저장소에서 |
|---|---|---|
| **JSON Lines · append-only** | 한 줄에 JSON 하나씩 덧붙이기만 하는 파일 형식이다. 고치거나 지우지 않는다. | 거래 원장 `logs/ledger.jsonl`(6.3절) |

| **배치 API** | 여러 건을 한 번의 요청으로 받는 API 다. | 복수시세 30종목/호출(2.4절) |

### 0.5 배포와 운영

| 용어 | 뜻 | 이 저장소에서 |
|---|---|---|
| **systemd · 서비스 유닛** | 리눅스에서 프로세스를 띄우고, 죽으면 다시 띄우고, 부팅 때 자동으로 켜 주는 관리자다. 유닛은 그 설정 파일이다. | `bankis.service`(8.1절) |
| **cgroup · MemoryMax · CPUQuota** | 프로세스 묶음이 쓸 수 있는 메모리·CPU 상한을 커널이 강제하는 기능이다. | 엔진 `MemoryMax=2G`, 수집 배치 `MemoryMax=1G`(8.1·9.3절) |
| **OOM killer** | 메모리가 바닥나면 커널이 프로세스 하나를 골라 강제로 죽이는 장치다. | cgroup 으로 엔진을 보호하는 이유(9.3절) |
| **로그 회전 · copytruncate** | 로그 파일을 날짜별로 잘라 오래된 것을 지우는 일이다. copytruncate 는 복사한 뒤 원본을 비우는 방식이다. | `/etc/logrotate.d/bankis`(8.3절) |
| **스왑** | 메모리가 모자랄 때 디스크 일부를 메모리처럼 쓰는 공간이다. 느리지만 OOM 을 늦춘다. | 1GB 스왑(8.3절) |
| **종료 코드 · set -euo pipefail** | 프로그램이 끝날 때 내는 숫자(0 이 성공)다. `set -e` 는 0 이 아니면 스크립트를 멈추고, `pipefail` 은 파이프 중간의 실패도 실패로 본다. | 배포 스크립트(8.2절) |
| **cron** | 정해진 시각에 명령을 돌려 주는 예약 실행기다. | 평일 15:40 원장 백업(8.3절) |
| **NTP · chrony** | 서버 시계를 인터넷 표준 시각에 맞추는 프로토콜과 그 프로그램이다. | `setup.sh` 의 chrony(7.3절) |

### 1.1 요청 하나가 지나가는 길

이 시스템이 하는 일을 한 문장으로 줄이면 "09:05 에 494종목의 거래대금을 보고, 조건을 넘은 종목을 사서, 거래가 식으면 판다"이다.
이 일을 하려면 증권사와 두 가지 방식으로 이야기해야 한다. 시세 조회와 주문은 REST 로 한 번씩 묻고 답을 받고,
실시간 시세와 체결 통보는 WebSocket 으로 계속 받는다.

어려운 점은 증권사가 **초당 1건**만 받아 준다는 것이다(모의투자 서버 실측, 3장). 그래서 모든 REST 요청은 반드시
유량 제어기를 먼저 지나간다. 매매 엔진이 "005930 현재가를 달라"고 하면 REST 클라이언트가 유량 제어기에서 토큰을
하나 받을 때까지 기다리고, 받으면 HTTPS 로 KIS 에 보낸다. 주문은 그 전에 리스크 관문을 통과해야 수량이 정해진다.
체결이 나면 WebSocket 체결 통보가 엔진으로 들어오고, 엔진은 그 결과를 원장 파일에 한 줄 적는다.

이 전부가 **프로세스 하나, 스레드 하나**(asyncio 이벤트 루프) 안에서 돈다. 엔진 메모리는 약 250MB 이다.
마이크로서비스로 나누지 않은 이유는 [포트폴리오 문서 4장](포트폴리오-자기소개서.md#4-하지-않은-것과-그-이유)에 수치와 함께 있다.

| `main.py` | `TradingEngine` — 위 부품을 묶어 루프를 돌린다 |

### 1.3 가짜 증권사와 진짜 증권사를 같은 코드로

**기초부터.** 외부 API 를 부르는 코드는 테스트하기 어렵다. 진짜 증권사에 주문을 넣어 볼 수는 없고, 장이 닫힌 밤에는
시세도 안 온다. 그래서 진짜와 **똑같은 모양으로 답하는 가짜**를 만들어 두고, 설정 하나로 바꿔 끼우는 방법을 쓴다.
이것을 의존성 주입이라고 부르기도 한다.

**이 프로젝트에서는.** `api/factory.py::create_broker()` 가 `.env` 의 `USE_MOCK_MODE` 를 보고 `MockKISClient` 나
`KISClient` 를 돌려준다. 둘 다 `AbstractBroker` 를 구현하고 **KIS 의 실제 JSON 필드 이름**(`rt_cd`·`msg_cd`·`output`)을
그대로 돌려준다. 그래서 엔진은 지금 상대가 진짜인지 가짜인지 모른다. 가짜도 유량 제어기를 똑같이 지나가게 해서,
실서버로 바꿨을 때 타이밍이 달라지지 않게 했다.

**실무에서는.** 결제·외부 API 가 있는 서비스는 대부분 이렇게 "어댑터"를 둔다. 가짜가 진짜와 어긋나면 테스트는 통과하고
운영에서 터진다. 그래서 가짜는 진짜의 실제 응답을 녹음해 두고 그 모양을 따라 만드는 것이 좋다.

> **직접 해보기** — `api/mock_client.py` 의 `inquire_balance` 가 돌려주는 필드와 `api/base.py::get_portfolio_state` 가 읽는 필드를 나란히 놓고, 가짜가 진짜 응답을 어디까지 흉내 내는지 확인한다.

## 2. 외부 API 연동

<!-- diagram: map@api,kis | 2장은 엔진과 증권사 사이에서 요청을 보내고 실패를 다루는 REST 클라이언트를 본다. -->

**지도에서 보면.** 1장에서 요청 하나가 유량 제어기와 REST 클라이언트를 지나 KIS 로 간다는 것을 봤다. 이 장은 그중
REST 클라이언트, 즉 엔진의 "조회해 줘·주문해 줘"를 HTTPS 요청으로 바꾸고 실패를 처리하는 부분을 본다.
유량 제어기는 바로 다음 장에서 따로 본다.

> **이 장에서 배울 것** — 외부 API 를 부를 때 무엇이 실패할 수 있고, 실패마다 어떻게 다르게 대응해야 하는지 본다. 특히 주문처럼 두 번 보내면 안 되는 요청을 다루는 법을 본다.
>
> **먼저 알아둘 말** — [HTTP 상태 코드 · 429 · 403](#01-웹과-네트워크) · [재시도 · 지수 백오프](#03-신뢰성과-장애-대응) · [멱등성](#03-신뢰성과-장애-대응)

### 2.1 모든 요청이 지나가는 한 경로

**기초부터.** 외부 API 를 부르는 코드가 여기저기 흩어져 있으면 재시도, 토큰 갱신, 시간 측정을 곳곳에 똑같이 넣어야 하고
한 곳은 꼭 빠진다. 그래서 모든 요청을 **함수 하나**로 모으고, 공통 처리는 그 안에서만 한다.

**이 프로젝트에서는.** `api/client.py::KISClient._request` 가 그 한 경로다. 요청 하나는 이 순서를 지난다. 먼저 유량
제어기에서 토큰을 받고(`self.limiter.acquire(priority)`), 시간을 재기 시작한 뒤 보낸다. 응답이 오면 걸린 시간을 TR(KIS 의 API
종류 이름)별로 기록한다(7.2절). 그다음 실패를 종류별로 나눠 처리한다. HTTP 429 나 KIS 오류 코드 `EGW00201`(초당 거래건수 초과)은
서버가 거절한 것이라 유량 제어기에 알려 속도를 줄이고 다시 보낸다. 토큰 오류(`EGW00121` 등)는 토큰을 강제로 새로 받아
한 번만 다시 보낸다. 통신 오류는 `HTTP_BACKOFF_BASE` 0.6초에서 시작해 두 배씩 기다리며 최대 `HTTP_MAX_RETRY` 3번까지 보낸다.

**실무에서는.** HTTP 클라이언트 라이브러리(httpx, OkHttp, Spring WebClient)는 대부분 재시도 기능을 갖고 있지만, "어떤 실패를
재시도해도 되는가"는 라이브러리가 모른다. 그 판단은 다음 절처럼 요청의 성질을 아는 쪽이 해야 한다.

### 2.2 인증 토큰은 만료 전에 미리 바꾼다

**기초부터.** 많은 API 는 앱 키로 **접근 토큰**을 받아 요청마다 붙이게 한다. 토큰은 일정 시간이 지나면 만료된다.
만료된 뒤에야 알아채면 그 순간의 요청이 실패한다. 그런데 토큰을 너무 자주 받으면 발급 API 자체가 막힌다.

**이 프로젝트에서는.** `core/auth.py::TokenManager` 가 토큰을 관리한다. 만료 **30분 전**(`REFRESH_MARGIN`)에 백그라운드
태스크가 미리 새 토큰을 받고, 재발급은 최소 70초 간격(`MIN_REISSUE_INTERVAL`)을 지킨다. 여러 코루틴이 동시에 토큰을 요청해도
락으로 묶어 발급은 한 번만 일어난다. 받은 토큰은 파일에 캐시해서 엔진을 재시작해도 다시 발급받지 않는다.

**실무에서는.** OAuth 접근 토큰을 쓰는 서비스는 모두 같은 문제를 겪는다. "만료 직전 선제 갱신 + 동시 갱신 방지 락 + 캐시"가
기본 모양이다. 서버 여러 대가 같은 토큰을 쓰면 캐시를 Redis 같은 공용 저장소로 옮긴다.

### 2.3 주문은 다시 보내면 안 된다 — 멱등성

**기초부터.** 조회는 열 번 보내도 결과가 같다. 이것을 멱등하다고 한다. 매수 주문은 다르다. 두 번 보내면 두 번 산다.
문제는 "응답을 못 받은" 경우다. 요청이 서버에 도착해 처리됐는데 답이 오는 길에 끊겼을 수도 있고, 요청 자체가 안 나갔을
수도 있다. 클라이언트는 둘을 구분할 수 없다. 그래서 무작정 재시도하면 이중 주문이 난다.

<!-- diagram: order_unknown | 주문 응답을 못 받았을 때, 요청이 나가지 않은 것이 확실한 경우만 재시도하고 나머지는 결과 불명으로 두고 대사로 확인한다. -->

```text
 주문 전송 ──▶ 응답 받음 ───────────────▶ 성공 · 거절 처리
     │
     └──▶ 응답 못 받음
             ├─ 접속 실패 · 접속 타임아웃 ──▶ 요청이 안 나갔다 ──▶ 재시도
             └─ 읽기 타임아웃 · 끊김 · 5xx ──▶ 결과 불명(LOCAL_UNKNOWN)
                                                 └──▶ 미체결·잔고 즉시 대조
```

**이 프로젝트에서는.** `_request` 는 `idempotent=False` 로 불리면(주문) 실패를 둘로 나눈다. 접속 실패·접속 타임아웃·커넥션 풀 대기
(`httpx.ConnectError`·`ConnectTimeout`·`PoolTimeout`)는 요청이 증권사에 닿지 않은 것이 확실하므로 재시도한다. 읽기 타임아웃,
연결 중 끊김, 5xx 는 처리됐을 수 있으므로 재시도하지 않고 `LOCAL_UNKNOWN` 이라는 자체 코드를 돌려준다. 엔진의 `_submit` 은
이 코드를 받으면 다시 보내지 않고 미체결 목록과 잔고를 **즉시 조회**해서 실제로 접수됐는지 확인한다(5.3절의 대사).
429 와 `EGW00201` 은 게이트웨이가 거절해 실행되지 않은 것이 확실하므로 주문도 재시도한다.

**실무에서는.** 결제 API 는 보통 **멱등 키**(Idempotency-Key 헤더)를 받는다. 같은 키로 두 번 오면 서버가 두 번째를 무시한다.
KIS 주문 API 에는 그런 키가 없어서 클라이언트 쪽에서 "모르면 다시 보내지 말고 확인한다"로 막았다.

> **직접 해보기** — `api/client.py::_request` 에서 `not_sent` 를 만드는 줄을 찾고, 읽기 타임아웃(`httpx.ReadTimeout`)이 왜 그 목록에 없는지 한 문장으로 설명해 본다.

### 2.4 호출 수를 줄이는 배치 API

**기초부터.** 유량이 초당 1건이면 284번 부르는 데 최소 284초가 걸린다. 네트워크를 아무리 빠르게 해도 소용없다.
이럴 때는 요청 하나의 속도가 아니라 **요청 개수**를 줄여야 한다. 여러 건을 한 번에 받는 배치 API 가 있으면 그것을 쓴다.

**이 프로젝트에서는.** 장 시작 판정은 처음에 종목마다 당일 분봉을 받았다. 284종목에 284호출, 실측 **305.0초**였다. KIS 에는 30종목의
현재가와 누적 거래대금을 한 번에 주는 복수시세(`FHKST11300006`)가 있다. `api/base.py::get_turnovers` 가 종목을 30개씩 묶어 부르고,
284종목이 10호출 **19.8초**가 됐다(15배). 494종목으로 늘린 지금은 17호출이다. 판정에 꼭 필요하지 않은 "내일 기준선용 분봉
기록"은 진입이 끝난 뒤 가장 낮은 우선순위로 미뤘다(`main.py::_record_opening_history`). 지연을 분해해서 이 결론에 이른 과정은
[포트폴리오 3-2](포트폴리오-자기소개서.md#3-2-장-시작-판정이-305초-걸렸다--지연을-분해해-보니-86가-대기열이었다)에 있다.

**실무에서는.** "N+1 쿼리" 문제와 같은 모양이다. 목록 하나를 가져온 뒤 항목마다 다시 묻는 대신 한 번에 묶어 묻는다.
GraphQL 의 DataLoader, JPA 의 fetch join 이 같은 생각이다.

## 3. 유량 제어

<!-- diagram: map@limiter,kis | 3장은 모든 REST 요청이 반드시 지나가는 유량 제어기를 본다. -->

**지도에서 보면.** 2장의 REST 클라이언트는 요청을 보내기 전에 반드시 유량 제어기에서 토큰을 받는다. 이 장은 그 유량 제어기,
즉 엔진과 KIS 사이의 "문지기"를 본다. 엔진의 처리 속도를 정하는 것은 CPU 도 네트워크도 아니고 이 문지기다.

> **이 장에서 배울 것** — 토큰 버킷으로 속도를 맞추는 법, 급한 요청을 먼저 보내는 법, 서버가 거절했을 때 물러서는 법을 본다. 그리고 문서의 한도를 믿지 않고 직접 잰 이야기를 본다.
>
> **먼저 알아둘 말** — [유량 제한(Rate Limit)](#03-신뢰성과-장애-대응) · [토큰 버킷](#03-신뢰성과-장애-대응) · [버스트](#03-신뢰성과-장애-대응) · [큐 · 우선순위 힙](#02-비동기와-동시성)

<!-- diagram: limiter | 요청은 우선순위 힙에서 기다리다가 토큰 버킷에서 토큰을 받아야 나가고, 서버가 거절하면 버킷을 비우고 페널티를 두 배씩 늘린다. -->

```text
 주문(P0) ┐
 계좌(P1) ├─▶ 우선순위 힙 ──▶ 토큰 버킷 ──▶ KIS
 시세(P2) ┤    급한 것부터     초당 1개 충전
 기록(P3) ┘                  바구니 크기 1
                                 ▲
             거절(EGW00201) ─────┘ 토큰 0 · 페널티 5→10→…→60초
```

### 3.1 토큰 버킷

**기초부터.** "초당 1건"을 지키는 가장 단순한 방법은 요청마다 1초씩 쉬는 것이다. 그런데 이렇게 하면 한동안 요청이 없다가
갑자기 몇 건이 와도 무조건 1초씩 줄을 선다. 토큰 버킷은 바구니에 토큰이 초당 일정 속도로 차고, 요청은 토큰 하나를 꺼내야
나갈 수 있게 하는 방식이다. 바구니가 크면 쉬는 동안 쌓인 토큰으로 몇 건을 한꺼번에 보낼 수 있다. 그 크기가 버스트다.

**이 프로젝트에서는.** `core/rate_limiter.py::PriorityRateLimiter` 가 토큰 버킷이다. `_refill` 이 지난 시간 × 속도만큼 토큰을 채우는데,
시간은 `time.monotonic()` 으로 잰다. 단조 시계는 NTP 가 시스템 시각을 앞뒤로 고쳐도 뒤로 가지 않으므로 토큰 계산이 튀지 않는다.
설정은 `.env` 의 `REST_RATE_LIMIT=1`, `REST_BURST=1` 이다.

**실무에서는.** API 게이트웨이(Nginx `limit_req`, AWS API Gateway, Spring Cloud Gateway)가 서버 쪽에서 같은 알고리즘을 쓴다.
클라이언트 쪽에서도 같은 것을 두는 이유는, 상대의 거절을 기다리는 것보다 미리 맞춰 보내는 것이 훨씬 싸기 때문이다.

### 3.2 급한 요청을 먼저 — 우선순위 힙

**기초부터.** 시세 조회 수백 건이 줄을 서 있는데 손절 주문이 그 뒤에 서면 수백 초 늦게 나간다. 그래서 대기열을 먼저 온 순서가
아니라 **급한 순서**로 꺼내야 한다. 파이썬 `heapq` 는 가장 작은 값을 빠르게 꺼내는 자료구조이고, 우선순위 숫자가 작을수록 급한 것으로 쓴다.

**이 프로젝트에서는.** 우선순위는 넷이다. 주문 `PRIORITY_ORDER=0`, 잔고 조회 `PRIORITY_ACCOUNT=1`, 시세 `PRIORITY_QUOTE=2`, 배경 작업
`PRIORITY_BACKGROUND=3` 이다. `acquire` 는 `(우선순위, 들어온 번호, Future)` 를 힙에 넣고 기다린다. 들어온 번호를 같이 넣는 이유는
같은 우선순위끼리는 먼저 온 것이 먼저 나가게 하기 위해서다. 디스패처 태스크(`_run`) 하나가 토큰이 생길 때마다 힙에서 하나를 꺼내
그 Future 를 깨운다. 기다리다 취소된 요청은 토큰을 쓰지 않고 버린다.

**실무에서는.** 우선순위만 있으면 낮은 우선순위가 영원히 못 나가는 기아(starvation)가 생길 수 있다. 이 엔진은 주문이 하루에 많아야 몇 건이라
문제가 안 되지만, 주문이 많은 시스템이면 우선순위별 최소 몫을 보장하는 가중 공정 큐(WFQ)를 쓴다.

### 3.3 거절당하면 물러선다 — 페널티와 지수 백오프

**기초부터.** 상대가 "너무 빠르다"고 거절했는데 같은 속도로 계속 보내면 거절만 쌓인다. 거절당하면 속도를 낮추고, 연달아 거절당하면
더 오래 쉰다. 쉬는 시간을 두 배씩 늘리는 것이 지수 백오프다.

**이 프로젝트에서는.** `notify_rate_limit_error` 는 거절을 받으면 바구니를 비우고(`self._tokens = 0.0`), 5초(`penalty_seconds`) 동안
속도를 절반(`penalty_factor=0.5`)으로 낮춘다. 페널티 중에 또 거절당하면 페널티를 두 배로 늘리되 60초(`max_penalty_seconds`)를 넘기지 않는다.
정상 응답이 오면 `notify_success` 가 페널티를 풀어 준다.

**실무에서는.** 여러 클라이언트가 동시에 거절당하고 똑같이 두 배씩 쉬면 동시에 다시 몰린다. 그래서 대기 시간에 무작위 값(지터)을 섞는 것이 보통이다.
이 엔진은 클라이언트가 하나뿐이라 지터를 넣지 않았다.

### 3.4 문서의 한도를 믿지 않고 직접 쟀다

KIS 문서에는 모의투자 서버 한도가 초당 2건으로 적혀 있다. 처음에는 10% 낮춰 초당 1.8건, 버스트 2 로 뒀는데, 실서버에 처음 붙인 날
기동 6분 동안 `EGW00201` 이 **74회** 났다. 로그를 보니 거절 → 5초 페널티 → 그동안 바구니가 다시 참 → 페널티가 끝나자마자 2건이 한꺼번에 나감 →
다시 거절, 이렇게 고리가 돌고 있었다.

추측으로는 원인을 가릴 수 없어서 같은 조회 30건을 일정 간격으로 보내고 거절 수를 셌다.

| 초당 요청 | 30건 중 거절 |
|---|---|
| 1.8 | 13 |
| 1.5 | 10 |
| 1.2 | 5 |
| **1.0** | **0** |

실효 한도는 초당 1건이었다. 1.2건에서도 거절이 나는 것은 서버가 1초 단위 고정 창으로 세기 때문으로 보인다. 요청 간격이 0.83초면
어떤 1초 창에는 2건이 들어간다. 그래서 속도를 1건으로, 버스트를 1로 낮췄고, 기동 시 거절은 0~3회가 됐다.
버스트를 1로 둔 것이 핵심이다. 페널티가 끝난 순간 몰려 나가는 요청이 사라진다.

> **직접 해보기** — `AsyncTokenBucket` 으로 속도 1.2, 바구니 1 짜리 버킷을 만들고 30번 `acquire` 한 시각을 찍어 본다. 그 시각들을 1초 단위로 잘랐을 때 2건이 들어간 창이 몇 개인지 세어 보면 고정 창 경계 문제가 눈에 보인다.

## 4. 실시간 연결 — WebSocket

<!-- diagram: map@ws,kis | 4장은 증권사와 연결을 열어 두고 실시간 시세·체결을 받는 WebSocket 클라이언트를 본다. -->

**지도에서 보면.** 2·3장의 REST 는 엔진이 물어야 답이 온다. 이 장은 지도에서 그 옆에 있는 WebSocket 클라이언트, 즉 증권사가
먼저 밀어 주는 실시간 시세와 체결 통보를 받는 쪽을 본다. 받은 것은 엔진으로 들어가 장부와 가격을 고친다.

> **이 장에서 배울 것** — 오래 열어 두는 연결은 반드시 끊긴다는 전제로, 끊겼을 때 다시 붙고 상태를 되살리는 법과 죽었을 때 다른 길로 돌아가는 법을 본다.
>
> **먼저 알아둘 말** — [WebSocket](#01-웹과-네트워크) · [재시도 · 지수 백오프](#03-신뢰성과-장애-대응) · [폴백](#03-신뢰성과-장애-대응)

### 4.1 왜 WebSocket 인가

**기초부터.** REST 로 실시간 가격을 보려면 몇 초마다 계속 물어야 한다(폴링). 유량이 초당 1건인 이 환경에서 40종목을 3초마다 물으면
한도를 13배 넘는다. WebSocket 은 연결을 한 번 열어 두면 서버가 값이 바뀔 때마다 밀어 주므로 요청 수가 들지 않는다.

**이 프로젝트에서는.** `core/websocket_client.py::KISWebSocketClient` 가 연결을 열고, 종목별 실시간 체결가(`H0STCNT0`)와 계좌 체결 통보(모의 `H0STCNI9`, 실전 `H0STCNI0`)를 구독한다.
KIS 는 연결당 구독 수에 한도가 있어 `WS_MAX_SUBSCRIPTIONS=40` 이다. 구독마다 우선순위를 두고, 자리가 차면 가장 덜 중요한 구독을 빼고 넣는다
(`_lowest_priority_sub`). 체결 통보는 AES 로 암호화돼 오므로 `_aes_cbc_decrypt` 로 푼다.

**실무에서는.** 채팅, 주식 시세, 협업 편집처럼 서버가 먼저 알려야 하는 서비스는 WebSocket 이나 SSE(서버가 보내기만 하는 단방향)를 쓴다.
서버를 여러 대로 늘리면 "이 사용자의 연결이 어느 서버에 붙어 있나"를 관리해야 해서 REST 보다 운영이 어렵다.

### 4.2 끊기면 다시 붙고, 구독을 되살린다

**기초부터.** 오래 열린 연결은 반드시 끊긴다. 상대 서버가 정기적으로 끊기도 하고, 중간 네트워크 장비가 조용한 연결을 정리하기도 한다.
다시 붙는 것만으로는 부족하다. 새 연결은 백지 상태라, 전에 구독하던 종목을 다시 등록해야 한다.

**이 프로젝트에서는.** `_run` 은 무한 반복 안에서 연결을 열고, 메시지를 받다가 예외가 나면 `delay` 초 기다렸다 다시 연다. `delay` 는 1초에서 시작해
실패할 때마다 두 배, 최대 `WS_RECONNECT_MAX_DELAY` 30초다. 연결에 성공하면 `delay` 를 1초로 되돌리고 `_resubscribe_all` 이 구독 목록을 우선순위 순서로
다시 등록한다. 서버 부하를 피하려고 등록 사이에 30ms 씩 쉰다.

실서버 로그를 보면 KIS WebSocket 은 **매시 정각에 서버 쪽에서 연결을 끊는다.** 10/13 21:00부터 10/14 12:00까지 17번 끊겼고(06:30 한 번 포함),
매번 1.0초 뒤 다시 붙어 구독 41건 복원까지 약 2.3초가 걸렸다. 설계할 때 이 주기를 알았던 것은 아니지만, "반드시 끊긴다"는 전제로 짠 재연결이
그대로 처리했다.

**실무에서는.** 재연결에 지수 백오프를 넣는 이유는 서버가 죽었을 때 수천 클라이언트가 1초마다 두드려 살아나는 서버를 다시 쓰러뜨리지 않게 하기 위해서다.
그리고 "재연결 후 상태 복원"을 빠뜨리는 것이 가장 흔한 실수다. 붙었는데 아무 데이터도 안 오는 상태가 된다.

### 4.3 조용하면 죽은 것으로 보고 REST 로 돌아간다

**기초부터.** 연결이 끊기면 예외가 나서 알 수 있지만, 연결은 살아 있는데 데이터만 안 오는 경우도 있다. 그래서 "마지막 메시지가 언제였나"를 본다.

**이 프로젝트에서는.** `is_healthy(max_silence=60.0)` 는 연결이 없거나 60초 넘게 메시지가 없으면 비정상으로 본다. 엔진의 `_refresh_quotes` 는
WebSocket 이 건강하면 그쪽이 덮는 종목의 REST 조회를 건너뛰고, 비정상이면 그 종목들을 REST 로 조회한다. 보유 종목은 루프마다 맨 앞에 넣어서
손절 판단에 쓰는 가격이 멈추지 않게 했다. 커널 쪽에서도 `tcp_keepalive_time=60` 으로 죽은 TCP 연결을 기본값 2시간이 아니라 약 2분 안에
정리하게 했다(8.4절).

**실무에서는.** 이렇게 응용 계층에서 보는 생존 확인을 하트비트라고 한다. TCP keepalive 는 "연결이 살아 있나"만 보고, 하트비트는 "상대가 일을 하고 있나"까지 본다. 둘 다 필요하다.

> **직접 해보기** — 서버 로그에서 `grep -E "WS\] (연결 오류|연결 성공)|구독 복원" logs/trader.log` 로 끊김·재연결·복원 시각을 뽑아, 끊김에서 복원까지 걸린 시간을 직접 계산해 본다.

## 5. 비동기 엔진과 상태

<!-- diagram: map@engine | 5장은 모든 부품을 묶어 3초마다 도는 매매 엔진 자체를 본다. -->

**지도에서 보면.** 2~4장에서 증권사와 이야기하는 부품들을 봤다. 이 장은 지도 한가운데의 매매 엔진, 즉 그 부품들을 하나의 이벤트 루프 위에서
엮어 3초마다 판단하고, 장부를 증권사와 맞추고, 죽었다 살아나도 이어 가게 하는 부분을 본다.

> **이 장에서 배울 것** — 스레드 하나로 여러 일을 동시에 처리하는 법, 느린 소비자 때문에 중요한 이벤트를 잃지 않는 법, 내 장부와 상대 장부를 맞추는 법, 깔끔하게 끄는 법을 본다.
>
> **먼저 알아둘 말** — [asyncio · 이벤트 루프](#02-비동기와-동시성) · [태스크 · 코루틴](#02-비동기와-동시성) · [대사(Reconcile)](#03-신뢰성과-장애-대응) · [그레이스풀 셧다운](#03-신뢰성과-장애-대응)

### 5.1 3초마다 도는 메인 루프와 곁가지 태스크

**기초부터.** 네트워크 응답을 기다리는 동안 CPU 는 할 일이 없다. 스레드를 여러 개 띄우면 기다리는 동안 다른 일을 할 수 있지만, 공유 자원에
락을 걸어야 해서 실수하기 쉽다. asyncio 는 스레드 하나에서 `await` 를 만날 때마다 "나는 기다릴 테니 다른 코루틴을 돌려라"라고 양보하게 한다.
락이 필요한 곳이 `await` 사이로 좁아져 훨씬 단순해진다. 대신 CPU 를 오래 쓰는 코드가 하나 끼면 전부 멈춘다.

**이 프로젝트에서는.** `main.py::TradingEngine.run` 은 `_tick()` 한 번을 돌고, 남은 시간만큼 `asyncio.wait_for(self._stop.wait(), timeout=...)` 으로
기다린다. 주기는 `LOOP_INTERVAL=3.0` 초다. 종료 신호가 오면 `_stop` 이벤트가 켜져 기다림이 바로 끝난다. `_tick` 안에서 예외가 나면 원장에
오류를 적고 1초부터 두 배씩(최대 30초) 쉰 뒤 다음 루프를 돈다. 한 번의 예외로 엔진 전체가 죽지 않게 한 것이다.

오래 걸리는 일은 루프 안에서 기다리지 않고 **태스크로 떼어 낸다.** 09:05 장 시작 판정(`_opening_scan`)은 494종목 복수시세 17호출로 약 20초가 걸린다.
이것을 루프 안에서 `await` 하면 그동안 손절 판단도 멈춘다. 그래서 `asyncio.create_task(self._opening_scan(now))` 로 띄우고 루프는 계속 돈다.
판정이 끝나면 결과(`_opening_picks`)를 다음 루프가 읽어 진입한다. 토큰 자동 갱신, WebSocket 수신, 이벤트 버스 소비자도 모두 따로 도는 태스크다.

**실무에서는.** 웹 서버(FastAPI, Node.js)도 같은 모델이다. "이벤트 루프를 막지 말라"가 첫째 규칙이고, 무거운 계산은 별도 프로세스나 스레드
풀(`run_in_executor`)로 보낸다.

### 5.2 이벤트 버스 — 시세는 버려도 체결은 버리지 않는다

**기초부터.** 생산자(WebSocket 수신)가 소비자(장부 갱신)보다 빠르면 큐가 끝없이 커져 메모리가 터진다. 그래서 큐에 크기 상한을 두고, 넘치면
무언가를 버린다. 무엇을 버릴지가 설계의 핵심이다. 시세는 최신 값만 의미가 있으니 오래된 것을 버려도 되지만, 체결 통보를 버리면 장부가 틀어진다.

<!-- diagram: eventbus | 체결·주문은 크기 제한 없는 무손실 큐로, 시세·신호는 가득 차면 오래된 것을 버리는 큐로 보내고 소비자를 따로 돌린다. -->

```text
               ┌─▶ 무손실 큐 (fill · order) ──▶ 소비자 A ──▶ 장부 갱신
 publish(토픽) ┤     크기 제한 없음
               └─▶ 손실 허용 큐 (quote · signal) ──▶ 소비자 B ──▶ 가격 갱신
                     10,000개 · 넘치면 가장 오래된 것 버림
```

**이 프로젝트에서는.** `core/events.py::EventBus` 는 큐를 둘 둔다. `fill`·`order` 토픽은 크기 제한 없는 무손실 큐로, 나머지는 `maxsize=10_000` 인
손실 허용 큐로 간다. 손실 허용 큐가 가득 차면 가장 오래된 것을 하나 꺼내 버리고 새것을 넣으며, 버린 수를 `dropped` 로 세어 `/metrics` 의
`kis_event_dropped` 로 내보낸다. 두 큐는 소비자 태스크가 따로 돌아서 시세가 밀려도 체결 처리가 늦어지지 않는다. 핸들러 하나가 예외를 내도
`try/except` 로 감싸 소비자 루프가 죽지 않는다.

예전에는 큐가 하나여서 가득 차면 토픽과 상관없이 가장 오래된 이벤트를 버렸다. 시세가 몰리면 체결 이벤트가 버려질 수 있는 구조였다.

**실무에서는.** Kafka 나 RabbitMQ 같은 메시지 브로커도 토픽마다 보존 정책을 다르게 둔다. "이 메시지를 잃으면 무엇이 틀어지나"를 메시지 종류마다
묻는 것이 시작이다.

### 5.3 대사 — 내 장부를 증권사 장부에 맞춘다

**기초부터.** 엔진은 체결 통보를 받아 내 장부를 고친다. 그런데 통보가 유실되거나, 사람이 앱에서 직접 주문하거나, 응답을 못 받은 주문(2.3절)이
있으면 내 장부와 증권사 장부가 어긋난다. 그래서 주기적으로 증권사 장부를 받아 와 맞춘다. 회계에서 은행 잔고와 장부를 맞추는 일과 같다.

**이 프로젝트에서는.** `RECONCILE_LOOPS=30` 루프(약 90초)마다 두 가지를 한다. `_sync_portfolio` 는 잔고 조회 결과로 수량이 다르면 증권사 쪽 수량으로
고치고, 내 장부에 없는 포지션은 편입하고, 증권사에 없는 포지션은 지운다. 현금도 증권사 값으로 덮는다. `_sync_open_orders` 는 미체결 목록으로
`open_orders` 를 다시 만들고, 접수 후 180초(`max_age_seconds`)가 지난 미체결은 취소한다. 호가에서 멀어진 지정가가 돈을 묶어 두지 않게 하기 위해서다.

이때 **증권사 응답의 어느 필드를 믿느냐**가 중요하다. 10/14 첫 진입 직후 엔진이 자산을 1억에서 1.9억(+91%)으로 읽었다. 현금을 예수금 총액(`dnca_tot_amt`)으로
읽고 있었는데, 이 값은 결제일(이틀 뒤) 전까지 당일 매수 대금이 빠지지 않는다. 현금 1억과 산 주식 9천만 원이 겹쳐 셈해진 것이다. 이틀 뒤 기준
예수금(`prvs_rcdl_excc_amt`)으로 바꿔 고쳤다(`api/base.py::get_portfolio_state`).

**실무에서는.** 결제·정산 시스템에는 거의 반드시 일일 대사 배치가 있다. 실시간 이벤트만 믿지 않고 "정답 장부"와 정기적으로 맞추는 것이 기본이다.
그리고 외부 응답의 숫자 필드는 "언제 기준의 값인가"까지 확인해야 한다.

### 5.4 깔끔하게 끄고, 이어서 켠다

**기초부터.** 프로세스를 그냥 죽이면 내던 주문이 미체결로 남고, 메모리에만 있던 값이 사라진다. 그래서 종료 신호(SIGTERM)를 받으면 하던 일을
정리하고 끄는 그레이스풀 셧다운을 한다. 다시 켤 때 이어 가야 하는 값은 디스크에 적어 둔다.

**이 프로젝트에서는.** `_install_signal_handlers` 가 SIGINT·SIGTERM 을 받으면 `_stop` 을 켠다. 루프가 끝나면 `shutdown` 이 순서대로 정리한다.
돌고 있는 판정·기록 태스크를 취소하고, 미체결 주문을 모두 취소하고, 남은 체결을 한 번 더 받고, `state/engine_state.json` 에 상태를 저장한 뒤
WebSocket·관제 화면·이벤트 버스·HTTP 클라이언트를 닫는다. 정리 단계 하나가 실패해도 나머지는 계속 정리한다(`_safe`). 서버의 systemd 는
`TimeoutStopSec=60` 으로 이 정리에 60초를 준다(8.1절).

상태 파일에는 각 종목의 **첫 매수일**(`entry_dates`)이 들어 있다. 청산 규칙이 "진입 당일은 판정하지 않는다"이므로, 재시작 뒤 이 값이 없으면
산 날 바로 팔 수 있다. 그래서 디스크가 차서 상태 파일을 못 쓰는 것이 위험하고, 남은 공간이 1GB 아래면 경고하게 했다(8.3절).

**실무에서는.** 쿠버네티스는 파드를 내릴 때 SIGTERM 을 보내고 `terminationGracePeriodSeconds`(기본 30초)를 기다린 뒤 SIGKILL 을 보낸다.
웹 서버라면 이 사이에 새 요청을 그만 받고, 처리 중인 요청을 끝내야 한다.

> **직접 해보기** — Mock 모드로 `python main.py --duration 60` 을 돌린 뒤 `state/engine_state.json` 을 열어 어떤 값이 저장되는지 보고, 그중 재시작 뒤에 없으면 안 되는 값을 골라 본다.

## 6. 주문과 장부

<!-- diagram: map@risk,ledger | 6장은 주문 수량을 최종 결정하는 리스크 관문과, 모든 판단을 남기는 원장을 본다. -->

**지도에서 보면.** 5장의 엔진이 "이 종목을 사자"고 판단하면 바로 주문이 나가지 않는다. 이 장은 지도에서 엔진 오른쪽의 리스크 관문과 그 아래의
원장, 즉 주문 수량을 정하는 관문과 그 결과를 지우지 않고 쌓는 기록을 본다.

> **이 장에서 배울 것** — 위험한 동작을 한 곳에서만 허락하게 만드는 관문 패턴과, 나중에 감사할 수 있는 기록을 남기는 법을 본다.
>
> **먼저 알아둘 말** — [JSON Lines · append-only](#04-데이터와-저장) · [락(Lock)](#02-비동기와-동시성)

### 6.1 주문 수량은 한 곳에서만 정한다 — 관문 패턴

**기초부터.** 돈이 나가는 경로가 여러 군데면 그중 하나는 한도 검사를 빠뜨린다. 그래서 "모든 매수는 반드시 이 함수를 지나야 한다"는 관문을 하나 두고,
다른 코드는 수량을 직접 정하지 못하게 한다.

**이 프로젝트에서는.** 전략은 점수만 내고, `strategy/risk_manager.py::RiskManager.evaluate_entry()` 가 `RiskDecision(approved, qty, ...)` 을 돌려줘야
주문이 나간다. 관문은 종목당·총 익스포저 상한, 가용 현금, 리스크 상태(NORMAL·DERISK·HALT)를 보고 수량을 깎거나 거절한다. 청산도
`evaluate_exits()` 한 곳에서 우선순위대로 정한다. 지수 종목 요건용 소액 매매처럼 새 매수 경로를 만들 때도 `evaluate_entry(max_notional=...)` 로
관문을 지나게 했다. 관문 안의 규칙은 주문도 네트워크도 모르는 순수 함수라 셀프테스트가 네트워크 없이 검증한다.

**실무에서는.** 결제 서비스의 한도·사기 탐지, 권한 검사(인가)가 같은 모양이다. "검사를 호출하는 쪽이 기억해야 하는" 구조보다 "관문을 지나지 않으면
실행할 방법이 없는" 구조가 안전하다.

### 6.2 지정가와 호가 단위

**기초부터.** 증권사는 아무 가격이나 받지 않는다. 가격대마다 호가 단위(예: 2만~5만 원은 50원)가 있고, 단위에 안 맞는 가격은 거절한다. 그리고 시장가 대신
지정가를 쓰면 "이 가격보다 비싸게는 안 산다"는 상한을 걸 수 있다.

**이 프로젝트에서는.** `main.py::_submit` 은 현재가에 매수 +2.0%(`BUY_LIMIT_BAND`), 매도 −0.4%(`SELL_LIMIT_BAND`)를 곱한 뒤
`utils/market_rules.py::round_to_tick()` 으로 호가 단위에 맞춘다. 매수 폭이 넓은 이유는 실측에서 +0.4% 로는 체결률이 61.5%뿐이었고 놓친 쪽이
가장 빠르게 오르는 종목이었기 때문이다. 지정가는 상한이라 대부분 그보다 싸게 체결된다. 10/14 첫 진입도 23,700원 지정가가 23,150~23,250원에 체결됐다.

**실무에서는.** 외부 시스템이 받는 값의 형식(호가 단위, 통화 소수점, 문자열 길이)을 클라이언트에서 먼저 맞추는 것은 거절과 재시도를 줄이는 가장 싼 방법이다.

### 6.3 원장 — 지우지 않고 덧붙이기만 하는 기록

**기초부터.** 나중에 "왜 이 주문이 나갔나"를 설명하려면 판단과 결과를 시간순으로 남겨야 한다. 고치거나 지울 수 있는 기록은 믿기 어렵다. 그래서 한 줄에 사건
하나씩 덧붙이기만 하는 append-only 로그를 쓴다.

**이 프로젝트에서는.** `utils/logger.py::JsonLedger` 가 `logs/ledger.jsonl` 에 `{"ts", "event", ...}` 한 줄씩 쓴다. 주문(`order`), 거절(`order_reject`),
결과 불명(`order_unknown`), 청산(`exit`), 오류(`error`)가 모두 여기에 남는다. 쓰기는 `threading.Lock` 으로 감싸 줄이 섞이지 않게 한다.
이 파일은 대회 근거자료라 로그 회전 대상에서 빼고 매일 따로 백업한다(8.3절).

**실무에서는.** 이벤트 소싱, 감사 로그, 데이터베이스의 WAL(Write-Ahead Log)이 같은 생각이다. 상태는 기록을 처음부터 다시 읽으면 언제든 만들 수 있다.

> **직접 해보기** — `logs/ledger.jsonl` 에서 `event` 별 개수를 세어 보고(`python -c` 한 줄이면 된다), `order` 와 체결이 짝이 맞는지 확인한다.

## 7. 관측 — 지표와 시계

<!-- diagram: map@monitor | 7장은 엔진의 상태를 숫자로 내보내는 관측 부분을 본다. -->

**지도에서 보면.** 지금까지 본 부품이 제대로 도는지는 바깥에서 볼 방법이 있어야 안다. 이 장은 지도에서 엔진 아래의 관측 부분, 즉 엔진 상태를
`/metrics` 로 내보내고 요청 지연과 시계 오차를 재는 곳을 본다.

> **이 장에서 배울 것** — 평균이 아니라 분위수로 지연을 보는 법, 적은 메모리로 분위수를 내는 법, 외부 서버와 내 시계가 맞는지 재는 법을 본다.
>
> **먼저 알아둘 말** — [지표(Metrics) · Prometheus 형식](#06-관측과-테스트) · [히스토그램 · 분위수(p50·p95·p99)](#06-관측과-테스트) · [NTP · chrony](#05-배포와-운영)

### 7.1 /metrics — 상태를 숫자로 내보낸다

**기초부터.** 로그는 사건을 문장으로 남기고, 지표는 상태를 숫자로 남긴다. "지금 유량 거절이 몇 번이었나"는 로그를 세는 것보다 카운터 하나를 보는 것이 빠르다.
Prometheus 형식은 `이름 값` 한 줄씩 쓰는 단순한 텍스트라, 어떤 수집 도구든 긁어 갈 수 있다.

**이 프로젝트에서는.** `monitor/app.py` 의 FastAPI 앱이 엔진과 **같은 이벤트 루프**에서 돌며 `GET /metrics` 로 자산, 낙폭, 보유 종목 수, 유량 거절 누적
(`kis_rate_limit_rejects`), 유량 평균 대기(`kis_rate_limit_wait_ms`), 버린 이벤트 수(`kis_event_dropped`), 시계 오차(`kis_clock_skew_seconds`), TR 별 지연
히스토그램을 내보낸다. 서버에서는 `127.0.0.1:8500` 에만 열려 있어서 바깥에서는 SSH 터널(`ssh -L 8500:127.0.0.1:8500`)로 본다.

**실무에서는.** 지표는 보통 RED(요청 수 Rate, 오류 Errors, 지연 Duration)와 USE(자원 사용률 Utilization, 포화 Saturation, 오류 Errors)로 고른다. 이 엔진에서 "포화"에 해당하는 것이 유량 대기 시간이다.

### 7.2 평균 말고 분위수 — 고정 버킷 히스토그램

**기초부터.** 요청 100개 중 99개가 100ms, 1개가 10초면 평균은 약 200ms 다. 평균만 보면 10초짜리를 놓친다. p99 를 보면 보인다. 그런데 분위수를 정확히
내려면 모든 값을 저장하고 정렬해야 한다. 장중 수만 건이면 메모리가 계속 는다.

**이 프로젝트에서는.** `core/latency.py` 는 Prometheus 히스토그램처럼 **고정 경계** 12개(10ms, 25ms, 50ms, … 10s)를 두고 각 구간에 들어온 개수만 센다.
분위수는 누적 개수가 그 비율을 넘는 구간의 경계값으로 근사한다. 메모리는 구간 수에 비례하고, 오차는 구간 간격만큼이다. "수십 ms 인가, 수백 ms 인가"를
가르기에는 충분했다. 실서버에서 이 지표로 요청 하나를 나눠 보니 왕복 평균은 144ms 인데 유량 대기 평균이 904ms 였다. 시간의 86% 가 대기열이었고,
그래서 네트워크가 아니라 호출 수를 줄였다(2.4절).

**실무에서는.** 여러 서버의 히스토그램은 구간별 개수를 더하기만 하면 합칠 수 있다. 서버마다 계산한 p99 는 평균 내면 틀린 값이 된다. 그래서 분위수가 아니라
히스토그램을 모은다.

### 7.3 시계 오차 — 09:05 를 믿을 수 있나

**기초부터.** 이 엔진은 "09:05 에 판정"처럼 시각으로 움직인다. 서버 시계가 몇 초 틀리면 다른 시점의 데이터로 판단한다. 서버 시계는 NTP(chrony)로 맞추고,
그래도 증권사 서버와 맞는지 따로 확인한다.

**이 프로젝트에서는.** `KISClient._measure_clock_skew` 는 첫 응답의 `Date` 헤더(증권사 서버 시각)와 로컬 시각을 비교한다. 요청이 가는 데 걸린 시간을 빼려고 왕복 시간의
절반을 보정한다. 오차가 2초를 넘으면 경고한다. `Date` 헤더는 1초 해상도라 1초 미만 오차는 의미가 없다. 실서버에서 chrony 오차는 17µs 였는데 이 값은 −0.96초로
나왔다. 헤더가 초 단위로 잘린 탓이다.

**실무에서는.** 분산 시스템에서 시각으로 순서를 정하면 서버마다 시계가 달라 틀린다. 그래서 "언제"가 중요한 곳은 NTP 동기화와 함께 오차 지표를 둔다.
순서만 필요하면 시각 대신 증가하는 번호(시퀀스, 논리 시계)를 쓴다.

> **직접 해보기** — 서버에 SSH 터널을 열고 `curl -s 127.0.0.1:8500/metrics | grep kis_http_request_seconds` 로 TR 별 지연 구간을 본 뒤, 누적 개수로 p95 가 어느 구간인지 손으로 계산해 본다.

### 8.1 systemd — 죽으면 다시 띄운다

**기초부터.** 터미널에서 `python main.py` 로 띄운 프로세스는 SSH 를 끊으면 같이 죽고, 서버가 재부팅되면 다시 안 뜬다. 죽었을 때 누가 다시 띄워 주지도 않는다.
systemd 는 리눅스의 프로세스 관리자로, 설정 파일(유닛) 하나로 이 셋을 해결한다.

**이 프로젝트에서는.** `deploy/oracle/setup.sh` 가 `/etc/systemd/system/bankis.service` 를 만든다. `Restart=always` 와 `RestartSec=30` 으로 죽으면 30초 뒤 다시 띄우고,
`After=network-online.target` 으로 네트워크가 올라온 뒤에 켠다. `TimeoutStopSec=60` 은 종료 신호 뒤 60초 동안 정리(5.4절)를 기다린다. `MemoryMax=2G` 는 cgroup 메모리
상한으로, 엔진 실측 RSS 약 250MB 의 8배다. 메모리가 새도 서버 전체가 아니라 이 서비스만 정리되고 다시 뜬다. 출력은 `logs/service.log` 로 보낸다.
설치 스크립트는 서비스를 **등록만 하고 켜지 않는다.** 같은 계좌에 엔진이 두 개 돌면 주문이 두 번 나가기 때문이다. 켜는 것은 `deploy.sh switch` 의 몫이다.

**실무에서는.** 컨테이너 환경에서는 쿠버네티스가 같은 일을 한다. `restartPolicy`, `resources.limits.memory`, `terminationGracePeriodSeconds` 가 각각
`Restart`, `MemoryMax`, `TimeoutStopSec` 에 대응한다.

### 8.2 배포 스크립트도 운영 코드다 — 종료 코드와 멱등성

**기초부터.** `set -euo pipefail` 은 셸 스크립트를 안전하게 만드는 세 가지 설정이다. `-e` 는 명령이 0 이 아닌 종료 코드를 내면 멈추고, `-u` 는 정의 안 된 변수를 쓰면
멈추고, `pipefail` 은 `a | b` 에서 `a` 가 실패해도 실패로 본다. 안전하지만, "실패가 아닌데 0 이 아닌 코드를 내는" 명령을 만나면 멀쩡한 배포가 멈춘다.

**이 프로젝트에서는.** 실제로 두 번 멈췄다. 첫째, 수집기가 쓰는 중인 폴더를 tar 로 묶자 GNU tar 가 `file changed as we read it` 과 함께 **종료 코드 1**을 냈다. tar 에서
1 은 "읽는 중 바뀜"이라는 경고이고 2 가 치명 오류다. 그래서 `push_data` 는 임시 파일로 먼저 묶고 종료 코드를 직접 보고, 1 이면 경고만 남기고 진행, 2 이상이면 멈춘다.
둘째, 다시 돌린 설치 스크립트가 "가상환경이 이미 있다"와 "crontab 이 비어 있어 `crontab -l` 이 1 을 냄" 때문에 멈췄다. 처음 한 번만 성공하도록 쓰인 스크립트였다.
가상환경은 있으면 건너뛰고(`[ -x .venv/bin/python ] || uv venv ...`), 빈 crontab 은 `{ crontab -l || true; }` 로 흡수했다. 이후 몇 번을 다시 돌려도 종료 코드 0 이다.

`deploy.sh` 의 모드는 넷이다. `setup` 은 코드·데이터를 보내고 설치만 한다. `code` 는 **커밋된** 코드만(`git archive HEAD`) 보내고 서비스를 재시작한다.
작업 중인 수정이 섞이지 않게 하기 위해서다. `switch` 는 노트북 엔진을 멈추고 꺼진 것을 확인한 뒤에야 서버 엔진을 켜며, 장중(08:30~15:40)에는 거부한다. `status` 는
상태와 최근 로그, 지표를 보여 준다.

**실무에서는.** Ansible, Terraform 같은 도구가 "몇 번을 돌려도 같은 상태"를 기본으로 하는 이유가 이것이다. 배포는 반드시 중간에 끊기고 다시 돌게 된다.

> **직접 해보기** — `deploy/oracle/deploy.sh` 의 `push_data` 에서 `rc` 를 다루는 세 줄을 읽고, `tar -cf - ... | ssh ...` 처럼 파이프로 바로 보내면 `pipefail` 아래에서 무엇이 달라지는지 설명해 본다.

### 8.3 10GB 디스크에서 30거래일 버티기

**기초부터.** 디스크는 조용히 찬다. 로그는 매일 쌓이고, 시스템 로그(journald)는 상한이 없으면 수 GB 까지 자라고, 패키지 설치 캐시도 남는다. 디스크가 차면 로그를 못 쓰는
것보다 **상태와 장부를 못 쓰는 것**이 더 위험하다.

**이 프로젝트에서는.** 서버 디스크는 10GB 이고 OS 가 4.0GB 를 쓰고 있었다. 그래서 항목별로 줄였다. 스왑은 2GB 에서 1GB 로(엔진 250MB, 메모리 3.8GB 라 2GB 는 과했다),
애플리케이션 로그는 하루 단위 14일 보관·압축(`/etc/logrotate.d/bankis`), journald 는 최대 200MB(`SystemMaxUse=200M`), 설치 캐시는 설치 직후 삭제했다. 로그 회전은
`copytruncate` 를 쓴다. 파일을 옮기지 않고 복사한 뒤 원본을 비우므로, 엔진이 열어 둔 파일 핸들이 계속 유효해서 재시작이 필요 없다. 대신 복사와 비우기 사이의 몇 줄을
잃을 수 있어서, 잃으면 안 되는 원장은 회전 대상에서 빼고 cron 으로 평일 15:40 에 압축 백업해 30일 보관한다. 엔진은 잔고 대조 때마다 남은 공간을 재고(`disk_free_gb`),
1GB 아래면 한 시간에 한 번 경고한다. 설치 후 남은 공간은 3.3GB 였고, 오늘(10/14) 기준 3.0GB 다.

**실무에서는.** 용량 산정은 "지금 얼마 쓰나"가 아니라 "하루에 얼마씩 느나 × 운영 기간"으로 한다. 그리고 꽉 차기 전에 경고가 와야 한다.

### 8.4 커널과 시계, 그리고 SSH

**기초부터.** 리눅스 기본값은 범용이라 이 서비스에 맞지 않는 것이 있다. TCP keepalive 기본값은 2시간 동안 조용해야 확인을 시작한다. 그 사이 죽은 연결을 붙잡고 있게 된다.

**이 프로젝트에서는.** `/etc/sysctl.d/90-bankis.conf` 에 `tcp_keepalive_time=60`, `intvl=10`, `probes=6` 을 넣어 죽은 연결을 약 2분(60초 + 10초 × 6) 안에 정리한다.
시계는 chrony 로 맞춘다(7.3절). SSH 는 키 로그인을 확인한 뒤 비밀번호 로그인을 끈다(`PasswordAuthentication no`). NCP 는 22번 포트를 바깥에 열어 두므로 비밀번호 대입
공격을 막기 위해서다. `.env`(앱 키·계좌)는 `chmod 600` 으로 소유자만 읽게 한다.

**실무에서는.** 서버를 만들 때마다 손으로 하던 이런 설정을 스크립트나 이미지로 굳혀 두는 것을 "골든 이미지" 또는 IaC(코드로 인프라 관리)라고 한다.

**지도에서 보면.** 지도 오른쪽 바깥의 수집 배치는 매매 엔진과 따로 돈다. 전략을 측정하려면 과거 분봉이 필요하고, 그것은 KIS 가 아니라 토스 API 에서 받는다.
이 장은 몇 시간짜리 배치 작업을 끊겨도 이어서 돌리고, 바뀌는 IP 를 서버로 고정하고, 실거래 서버에서 돌려도 엔진을 해치지 않게 하는 법을 본다.

> **이 장에서 배울 것** — 중단돼도 다시 돌리면 되는 배치를 만드는 법, IP 화이트리스트를 출발 IP 고정으로 푸는 법, 운영 서버에서 배치를 자원 상한으로 격리하는 법을 본다.
>
> **먼저 알아둘 말** — [멱등성](#03-신뢰성과-장애-대응) · [IP 화이트리스트 · egress IP](#01-웹과-네트워크) · [프록시 · SOCKS5 · SSH 터널](#01-웹과-네트워크) · [cgroup · MemoryMax · CPUQuota](#05-배포와-운영) · [OOM killer](#05-배포와-운영)

### 9.1 끊겨도 다시 돌리면 된다 — 이어받기

**기초부터.** 몇 시간 걸리는 배치는 반드시 중간에 끊긴다. 처음부터 다시 받으면 시간이 두 배가 되고, 중간 결과를 덮어쓰다 망가뜨릴 수도 있다. 그래서 "이미 한 일은 건너뛰는"
멱등한 배치로 만든다. 그러면 복구 절차가 "다시 띄운다" 한 줄이 된다.

**이 프로젝트에서는.** `scripts/collect_opening.py` 는 종목마다 파일 하나(`data/cache/opening/종목.csv`)에 저장하고, 시작할 때 파일에 이미 있는 날짜는 호출하지 않는다.
로그에 `기존 N` 으로 건너뛴 수가 찍힌다. 10/13 밤 노트북 수집이 440/494종목에서 오류 로그 없이 끝나 있었는데, 다음 날 다시 띄우자 받아 둔 440종목을 **호출 0건**으로
2분 만에 지나갔고 남은 54종목만 받았다. 토스가 429(유량 초과)를 내면 `Retry-After` 헤더만큼(없으면 1초) 쉬고 다시 보낸다(`api/toss_data.py::_get`).

**실무에서는.** 데이터 파이프라인(Airflow, Spark)에서 작업을 날짜 단위로 쪼개고 "그 날짜의 결과가 있으면 건너뛴다"로 만드는 것이 같은 생각이다. 더 엄격하게 하려면 임시 이름으로
쓴 뒤 다 쓰면 원자적으로 이름을 바꿔(rename), 반쯤 쓴 파일이 "이미 있음"으로 읽히지 않게 한다.

### 9.2 바뀌는 IP 를 서버로 고정한다 — SSH SOCKS 터널

**기초부터.** IP 화이트리스트는 "누가 보냈나"를 보지 않는다. 패킷의 출발지 IP 만 본다. 가정용 회선은 ISP 가 공인 IP 를 수시로 바꾸므로, 바뀔 때마다 새 IP 를 등록해야 한다.
근본 해결은 등록을 빨리 하는 것이 아니라 **출발 IP 를 바뀌지 않는 곳으로 모으는 것**이다.

<!-- diagram: socks | 노트북 수집기의 토스 요청만 로컬 1080 포트의 SOCKS 프록시를 거쳐 SSH 터널로 서버에 가고, 서버에서 나가므로 토스는 서버 IP 를 본다. -->

```text
 노트북                                   NCP 서버                토스 API
 ┌────────────┐  127.0.0.1:1080  ┌──────┐  SSH 22  ┌────────┐ HTTPS ┌──────┐
 │ 수집기       │────────────────▶│ ssh -D │────────▶│ sshd    │──────▶│ 화이트 │
 │ ALL_PROXY=… │     SOCKS5       └──────┘   암호화   └────────┘ 출발IP │ 리스트 │
 └────────────┘                                     = 서버 IP          └──────┘
   데이터는 노트북에 저장                     서버 설정 변경 없음
```

**이 프로젝트에서는.** 10/14 하루에만 노트북 공인 IP 가 3개 관측됐고, 바뀔 때마다 토스가 `403 IP address not allowed` 로 막았다. 11:37~11:45 에 6회 막혀 수집이 22분 멈췄다.
고정 공인 IP 를 가진 곳은 이미 있었다. 실거래 서버다. 서버에서 직접 수집하는 방법은 하루 전체 분봉이 279종목에 2.2GB 인데 서버 남은 공간이 3.0GB 라 뺐고, VPN 은 실거래 서버의
네트워크 설정을 바꿔야 해서 뺐다. 남은 것이 SSH 동적 포트 포워딩이다.

노트북에서 `ssh -N -D 127.0.0.1:1080 root@서버` 를 띄우면 로컬 1080 포트에 SOCKS5 프록시가 생기고, 그리로 들어온 연결은 SSH 터널을 지나 **서버에서** 바깥으로 나간다.
수집기에는 환경변수 `ALL_PROXY=socks5://127.0.0.1:1080` 만 준다. httpx 가 이 표준 환경변수를 읽으므로 코드는 한 줄도 바꾸지 않았다(SOCKS 지원 패키지 `socksio` 만 설치).
`ServerAliveInterval=30`, `ServerAliveCountMax=3` 으로 응답 없는 터널을 90초 안에 끊긴 것으로 판정하고, 재시작 스크립트가 매 시도 전에 1080 포트에 접속해 보고 죽었으면 터널을 다시 연다.
전환 뒤 `403` 은 0회, 회선이 끊겼을 때 실패했던 하루치 요청 365건은 다시 받아 실패 0건이다.

**실무에서는.** 회사에서는 이 역할을 NAT 게이트웨이나 고정 IP 프록시 서버가 한다. 외부 파트너 API 가 화이트리스트를 요구하면, 여러 서버의 요청을 NAT 게이트웨이 하나로 모아 그 IP 하나만 등록한다.

> **직접 해보기** — 터널을 연 뒤 `curl --socks5-hostname 127.0.0.1:1080 https://api.ipify.org` 와 그냥 `curl https://api.ipify.org` 의 결과를 비교해 출발 IP 가 바뀌는 것을 확인한다.

### 9.3 실거래 서버에서 배치를 돌릴 때 — cgroup 으로 격리

**기초부터.** 운영 서버에서 무거운 배치를 같이 돌리면 CPU 와 메모리를 나눠 쓴다. `nice` 로 우선순위를 낮추면 CPU 경쟁에서는 양보하지만 메모리는 막지 못한다. 배치가 메모리를 키우면
커널의 OOM killer 가 메모리를 가장 많이 쓰는 프로세스를 골라 죽이는데, 그것이 운영 서비스일 수 있다. 메모리 상한은 cgroup 으로 걸어야 하고, 상한을 넘으면 그 cgroup 안에서만 정리가 일어난다.

**이 프로젝트에서는.** 10/14 09:07, 09:10 판정을 3분 앞두고 실거래 서버에서 수집을 돌려야 했다. 먼저 두 작업이 같은 외부 한도를 나눠 쓰는지 봤다. 수집은 토스, 엔진은 KIS 라 유량 버킷은
겹치지 않는다. 남는 경쟁은 CPU·메모리여서 systemd 임시 유닛으로 띄웠다. 엔진 서비스와 다른 cgroup 이다.

```bash
systemd-run --unit=bankis-collect --nice=19 -p MemoryMax=1G -p CPUQuota=60% \
  -E UNIVERSE_FILE=config/universe_10b.json \
  .venv/bin/python scripts/collect_opening.py --since 20250102 --concurrency 3
```

`CPUQuota=60%` 는 코어 하나의 60% 라 2코어 중 최소 1.4코어를 엔진 몫으로 남긴다. 남은 54종목을 요청 8,657건으로 실패 0건, 17분 13초에 받았고, 수집기가 쓴 CPU 는 63.95초(한 코어의 약 6%),
서버 메모리는 674MB 에서 870MB 로 늘었다. 엔진의 판정은 수집이 도는 중에 09:10:17 에 끝났다.

**실무에서는.** 쿠버네티스의 `resources.requests/limits` 가 같은 일을 한다. 배치와 서비스를 같은 노드에 둘 때는 배치에 상한을 걸거나, 아예 노드를 나눈다(taint·toleration).

## 10. 검증

<!-- diagram: map@engine,risk | 10장은 엔진과 리스크 관문의 로직을 네트워크 없이 검증하는 셀프테스트와, 실전 직전 점검을 본다. -->

**지도에서 보면.** 지도의 어느 부품이든 바꾸면 다른 부품이 깨질 수 있다. 이 장은 지도 전체를 대상으로, 특히 엔진과 리스크 관문의 순수 로직을 네트워크 없이 검증하는 셀프테스트와,
실서버에 나가기 전 설정·데이터를 보는 프리플라이트를 본다.

> **이 장에서 배울 것** — 외부 API 없이 로직을 검증하는 법, 테스트가 환경(설정)에 흔들리지 않게 하는 법, 측정 결과를 비교해도 되는지 확인하는 법을 본다.
>
> **먼저 알아둘 말** — [셀프테스트 · 프리플라이트](#06-관측과-테스트) · [룩어헤드](#06-관측과-테스트) · [데이터 지문](#04-데이터와-저장)

### 10.1 셀프테스트 — 네트워크 없이 26개 항목

**기초부터.** 외부 API 를 부르는 테스트는 느리고, 장이 닫히면 안 되고, 진짜 주문을 낼 수도 있다. 그래서 판단 로직을 네트워크와 분리된 순수 함수로 두고, 그것만 따로 검증한다.

**이 프로젝트에서는.** `python scripts/selftest.py` 가 26개 항목을 돈다. pytest 를 쓰지 않고 `@check("이름")` 데코레이터로 등록한 함수를 차례로 부른다. 유량 제어기의 실측 속도(4번),
우선순위 큐에서 주문이 먼저 나가는지(5번), 가짜 증권사의 체결·거부·취소(6번), 리스크 관문(7번), 이벤트 버스(10번), 실서버 클라이언트의 오프라인 검증(11번), 주문 멱등성·무손실 채널·지연
지표(26번)를 본다. 테스트가 단정하는 값은 `.env` 가 아니라 코드의 기본값(`Settings.model_fields[...].default`)으로 고정한다(`make_settings`). `.env` 에서 사이징 방식을 바꾸자 변동성 타게팅 검증이 깨진 적이 있는데, 코드 버그가 아니라 설정 변경이었다.
테스트가 원장·로그·상태 파일을 임시 폴더에 쓰게 해서 실거래 원장을 건드리지 않는다.

**실무에서는.** 테스트 피라미드의 아래층(단위 테스트)을 두껍게 하는 이유가 이것이다. 외부 의존은 가짜로 바꾸고, 테스트는 운영 자원(DB·파일·외부 API)에 절대 쓰지 않는다.

### 10.2 프리플라이트 — 나가기 전 점검표

**기초부터.** 코드가 맞아도 설정이 틀리면 운영에서 틀린다. 예를 들어 감시 종목 수 상한이 유니버스보다 작으면 일부 종목을 조용히 안 본다. 이런 것은 테스트가 아니라 점검표로 잡는다.

**이 프로젝트에서는.** `python scripts/preflight.py` 가 설정·데이터·모드 조합을 보고 `[ OK ]`·`[WARN]`·치명으로 나눠 찍는다. 치명이 하나라도 있으면 실전에 나가지 않는다.
494종목으로 바꿀 때 `UNIVERSE_SIZE` 가 400 이면 "폭증 감시 범위"가 치명으로 막는다. 10/14 새 설정(판정 5분, 494종목)으로 돌렸을 때 치명 0건, 경고 2건이었다.

**실무에서는.** 배포 파이프라인의 스모크 테스트와 설정 검증(스키마 검사, 필수 환경변수 확인)이 같은 역할이다. 서버가 뜨자마자 설정이 틀렸으면 바로 죽게(fail fast) 하는 것이 좋다.

### 10.3 미래를 보지 않는다, 같은 데이터끼리만 비교한다

**기초부터.** 과거 데이터로 전략을 측정할 때, 그 시점에는 몰랐던 값(미래)을 계산에 쓰면 결과가 부풀려진다. 이것을 룩어헤드라고 한다. 그리고 데이터가 달라진 두 측정을 비교하면 코드 차이가
아니라 데이터 차이를 보게 된다.

**이 프로젝트에서는.** 셀프테스트 3번은 지표를 전체 구간에서 한 번 계산한 값과, 시점마다 잘라서 계산한 값이 같은지 본다. 다르면 어딘가에서 미래를 보고 있다. 측정 스크립트는 실행마다 데이터 지문
(정렬한 값의 MD5 와 종목·날짜 수)을 찍고, 지문이 다른 결과는 비교하지 않는다. 같은 코드가 +0.557% 와 −0.442% 로 갈린 적이 있는데, 원인은 수집이 도는 중에 측정해서 데이터가 바뀐 것이었다.
그래서 **수집이 끝난 뒤에만 측정한다.**

**실무에서는.** A/B 테스트와 성능 회귀 측정도 같다. 환경(데이터, 하드웨어, 트래픽)을 고정하지 않고 비교한 숫자는 믿을 수 없다.

## 11. 공부 순서와 면접

### 11.1 이 저장소로 공부하는 순서

1. **3장 유량 제어** — `core/rate_limiter.py` 는 270줄로 짧고 토큰 버킷, 우선순위 힙, 지수 백오프, 단조 시계가 다 들어 있다. 가장 먼저 읽는다
2. **2장 외부 API** — `api/client.py::_request` 한 함수에서 재시도·토큰·멱등성이 어떻게 갈리는지 본다
3. **5장 엔진** — `main.py::run`·`shutdown` 과 `core/events.py::EventBus` 로 asyncio 의 태스크·큐·종료를 본다
4. **4장 WebSocket** — `_run` 의 재연결 반복과 `_resubscribe_all` 을 본다
5. **8·9장 운영** — `deploy/oracle/setup.sh` 를 위에서 아래로 읽으며 각 줄이 무엇을 막는지 적어 본다
6. **7장 관측** — `core/latency.py` 로 히스토그램 분위수를 직접 계산해 본다

### 11.2 면접에서 나올 만한 질문

| 질문 | 답의 뼈대(본문 절) |
|---|---|
| 유량 한도를 문서보다 낮게 잡은 이유는? | 1.2건/초에서도 30건 중 5건 거절, 거절 1회 = 5초 페널티라 오히려 처리량이 줄었다(3.4절) |
| 평균 속도가 한도 아래인데 왜 거절됐나? | 서버의 1초 고정 창과 클라이언트의 연속 충전이 어긋나고, 버스트가 2면 페널티 직후 한꺼번에 나간다(3.4절) |
| 주문을 재시도하지 않는 경우는? | 응답을 못 받았지만 요청이 나갔을 수 있는 경우. 결과 불명으로 두고 대사로 확인한다(2.3절) |
| 이벤트를 버려도 되는 경우와 안 되는 경우는? | 시세는 최신 값만 의미가 있어 버려도 되고, 체결은 장부가 틀어져 안 된다. 큐를 둘로 나눴다(5.2절) |
| WebSocket 이 끊기면? | 1초부터 두 배씩 최대 30초 재연결, 붙으면 구독 복원, 60초 조용하면 REST 폴백(4장) |
| 평균 대신 p99 를 보는 이유와 메모리 문제는? | 평균은 꼬리를 숨긴다. 고정 버킷 히스토그램으로 메모리 O(버킷)로 근사한다(7.2절) |
| `copytruncate` 의 단점은? | 복사와 비우기 사이의 로그를 잃을 수 있다. 그래서 원장은 회전에서 빼고 따로 백업한다(8.3절) |
| 운영 서버에서 배치를 돌릴 때 `nice` 로 충분한가? | CPU 만 양보하고 메모리는 못 막는다. cgroup `MemoryMax` 로 OOM 을 배치 안에 가둔다(9.3절) |
| IP 화이트리스트가 있는 API 를 동적 IP 에서 쓰려면? | 출발 IP 를 고정 서버로 모은다. 이미 열린 SSH 의 `-D` 로 SOCKS 프록시를 만들었다(9.2절) |

같은 사례를 자기소개서용 문단과 숫자 근거표로 정리한 것은 [포트폴리오-자기소개서.md](포트폴리오-자기소개서.md)에 있다.
